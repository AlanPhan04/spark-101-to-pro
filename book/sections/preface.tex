\chapter{Preface}
\label{ch:preface}

This book began as a study journal. I run Spark SQL on an Apache Iceberg
lakehouse every working day, and I kept noticing the same thing about how I, and
the people around me, fixed slow queries. We changed a setting, ran the query
again, kept the change if it helped, and moved on without knowing why it had. That
works while a query takes a minute. It stops working when each trial takes an hour
and costs real money, and it stops working entirely when the setting that helped
last quarter makes this quarter's query slower.

I wanted to replace that trial loop with an understanding. The notes I kept while
learning turned into this book, and I wrote it for the person I was when I
started: someone comfortable with Python and SQL, with no idea what a cluster
actually does with a query.

\section*{One idea}

The whole book rests on one sentence, and every chapter is a consequence of it:

\begin{quote}
\itshape
Every Spark performance decision is a choice about where and when data moves,
and you can predict and change those movements once you can see them.
\end{quote}

Here is what that looks like in practice. A query reads files. When two rows must
meet, for a join or a group, Spark ships one of them across the network. Spark can
change its plan after it has seen how big the data really is. A table format such
as Iceberg lets the planner read a few kilobytes of metadata so that it does not
have to read gigabytes of data. These sound like separate subjects, and most
material treats them that way. They are one subject. Once you see it that way, the
question you ask of a slow query changes from ``which setting should I try?'' to
``what is moving, how much, and does it have to?''

\section*{What makes this book different}

There are good books on Spark and good material on Iceberg. This one makes two
commitments.

\paragraph{Mechanism before settings.} This is not a list of
\texttt{spark.sql.*} keys with recommended values. A setting appears only after the
mechanism it controls has been explained, and always with what it costs. A reader
who finishes should be able to work out most recommended values from first
principles, and to recognize the case where a recommendation is wrong. When a rule
of thumb is useful, and some are, the book shows where it comes from.

\paragraph{The seam between the engine and the table.} Most of the cost of a
lakehouse query is decided where the query engine meets the table format: what the
planner can push into the scan, what the metadata lets it skip, and how the files
written last night shape the work done this morning. Treating Spark and Iceberg as
two subjects hides that boundary. This book is built around it, with Part~II
covering the Spark side and Part~III the Iceberg side.

\section*{One query, and numbers you can reproduce}

The book follows one query, introduced in \Cref{ch:shape}: a week of orders joined
to a product table and summarized as an on-time delivery rate. On the
production-sized cluster it takes about four minutes. The first chapter does not
try to make it faster. It teaches you to \emph{read} it: the plan, the stages, the
shuffle, the one task that runs longer than the rest. Then every chapter changes
one thing about the query and shows what happened.

Wherever I could, I measured instead of asserting. The experiments run on one
machine, in a Docker container with Spark 3.5.2 and Iceberg 1.6.1, against
synthetic data shaped like the production tables (\Cref{sec:refenv-lab}). The
scripts live alongside the manuscript, so you can run them too.

Several times the measurement contradicted what I had written from memory. A
default I believed applied did not fire. A threshold compared a different quantity
than I had assumed. A mechanism needed a second setting before it did anything.
Those corrections are in the text, where they belong. The gap between what a
setting is documented to do and what it does on your data is where tuning goes
wrong.

Some claims I have not tested. They are marked ``claim --- not tested'' or
``verify on your cluster'' rather than smoothed over. Treat them as hypotheses.

\section*{A note on scope}

The book is written against one stack, and it says so every time a claim depends
on it. Spark and Iceberg both change quickly, and behavior that is true on 3.5.2
may not be true on 4.0. I would rather give you a model you can re-test against
your version than a table of values that quietly goes stale.
