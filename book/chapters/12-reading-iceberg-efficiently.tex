\chapter{Reading Iceberg Efficiently}
\label{ch:iceberg-read}

\begin{chapterintro}
Before the Iceberg reader opens a single data file, it has already skipped most
of them --- by partition, by manifest, by column statistics, and optionally by
bloom filter. Each layer needs the query's filter in a form it understands, and
each reports what it skipped. A week of \texttt{orders} opens 7 of 31 files; a
lookup of one \texttt{customer\_id} opens all 10 files of an unsorted table and
exactly one of the same rows sorted. This chapter covers the pruning layers, the
statistics that feed them, the counters that prove they fired, and the read-time
settings that decide how many tasks a scan becomes. Every number is a capture
from the lab of \Cref{sec:refenv-lab}.
\end{chapterintro}

\section{Manifest pruning and metadata filtering}
\label{sec:ice-read-manifest-pruning}

A scan resolves in layers, each cheaper than the last and each capable of
excluding the whole layer below it (\Cref{tab:ice-pruning-layers} lists them top
to bottom): the manifest list's per-manifest partition summaries
(\Cref{sec:ice-spec-v2}) let the planner skip an entire manifest without opening
it; the surviving manifests' per-file partition values and column statistics let
it skip individual files without opening them; only files that survive both
layers are opened at all, and even then column pruning
(\Cref{sec:pruning-column}) and row-group statistics (\Cref{sec:c-pushdown}) keep
working exactly as they do for any Parquet scan. Static and dynamic partition
pruning (\Cref{ch:pruning}) produce the values these layers filter against; this
chapter is about what Iceberg does with a value once Spark has produced one.

\begin{table}[htbp]
\centering
\caption{The pruning layers a scan passes through, in order}
\label{tab:ice-pruning-layers}
\begin{tabular}{@{}lP{7.5cm}@{}}
\toprule
\textbf{Layer} & \textbf{Skips} \\
\midrule
Manifest list & Whole manifests, via per-manifest partition summaries \\
Manifest entries & Whole data/delete files, via partition value and column
  min/max/null statistics \\
Bloom filter (optional) & Row groups, for an equality lookup on a
  high-cardinality column \\
Row-group statistics & Row groups within an opened file, via Parquet's own
  min/max (\Cref{sec:c-pushdown}) \\
\bottomrule
\end{tabular}
\end{table}

\Cref{fig:pruning-layers-funnel} draws the same four layers as what they are: a
funnel, narrowing from every file in the table down to the rows a query actually
reads, each layer paying only for what survived the one above it.

  \centering
  \includegraphics[width=\linewidth]{pruning-layers-funnel.pdf}

  has to consider what the layer above it did not already exclude --- a file

\subsection{Counting what each layer skipped}

Each layer reports its work as counters on the scan node: in the Spark UI's
\textbf{SQL} tab, the \texttt{BatchScan} box lists them as metrics, and they are
\emph{not} part of \texttt{EXPLAIN}. \Cref{fig:scan-metrics} reads them for the
specimen's week on a table built by 31 daily commits.

\begin{figure}[htbp]

The result is the same, and the cost is not: opening one manifest to inspect 31
entries is cheap, but a table with thousands of manifests turns the first layer
from a convenience into the thing that keeps planning fast. It works only when
manifests are clustered by partition, as they are for a daily load. After
streaming commits or many small appends each manifest spans many days, its
partition summary covers the whole range, and nothing is skipped; rewriting
manifests restores the clustering (\Cref{ch:iceberg-write}).

\section{Column statistics and predicate pushdown into Iceberg}
\label{sec:ice-read-stats}

Partition values are the easy case, because the partition column is the layout.
The second layer works for any column, but only if the statistics can tell files
apart. The per-file minimum and maximum of \texttt{product\_id} on the lab's
\texttt{orders} are a good example of statistics that cannot:

\begin{lstlisting}[language=text,numbers=none,style=plan,caption={Per-file bounds for three \texttt{orders} files (\texttt{readable\_metrics} of the \texttt{files} table, trimmed)},captionpos=b,label=lst:ice-read-bounds]
file (day)   order_id (lo .. hi)                product_id (lo .. hi)
03-01        000004a2-29b7-4d .. ffffcf0b-ec3e-4e   p0000005 .. p1999998
03-02        00000221-2318-41 .. ffffa331-4b9b-4f   p0000001 .. p1999999
03-03        000003c6-0c3e-41 .. ffffed77-6266-4g   p0000004 .. p1999998
\end{lstlisting}

Every file's range covers the whole key space, because rows were written in
arrival order and every day contains every product. A predicate \texttt{product\_id =
'p0000042'} is not outside any file's range, so no file is skipped. Pruning by
statistics is a property of the \emph{clustering} of the data, not of the
predicate. \Cref{fig:file-stat-ranges} measures it with a lookup of one
\texttt{customer\_id} on a 10-day copy of \texttt{orders} written two ways.

\begin{figure}[htbp]

Sorting is the strongest lever by a wide margin: 0.2~MB read against 60.5~MB. It
has a price the table also shows. The sorted copy is 200 files of 1.7~MB each
instead of 10 files of 35~MB, a small-files layout that costs planning time and
file opens on every other query (\Cref{sec:ice-file-size}). Choosing a sort
order is choosing which lookups you are willing to make cheap
(\Cref{ch:iceberg-layout}).

A filter that cannot be pushed to this layer still runs correctly --- Spark
applies it after the read --- so what is lost is pruning, never correctness. The
rules for what pushes down are the same as for plain Parquet, catalogued in
\Cref{sec:c-pushdown}.

\section{Metrics modes: \texttt{full}, \texttt{truncate}, \texttt{counts}, \texttt{none}}
\label{sec:ice-read-metrics-modes}

\conf{write.metadata.metrics.default} (default \texttt{truncate(16)})
controls how much of each column's statistics get written into the manifest in
the first place. It is a write-time property with a direct read-time consequence:

\begin{description}
  \item[\texttt{full}] stores the exact min and max value, uncapped. Best
        pruning, largest manifest entries --- expensive for a wide string
        column with long values.
  \item[\texttt{truncate(16)}] (the default) stores only the first 16 bytes of a
        string's min and max. Pruning still works for any predicate that
        differs within the first 16 bytes; two values agreeing on their first 16
        bytes look identical to the pruning layer.
  \item[\texttt{counts}] keeps null and value counts only, no min/max at all.
  \item[\texttt{none}] keeps nothing; the file is never skipped by this layer
        regardless of the filter.
\end{description}

The lab's \texttt{order\_id} is a 36-character UUID, and \Cref{lst:ice-read-bounds}
shows the truncation at work: every bound is exactly 16 characters. The upper
bound of the third file ends in \texttt{4g}, not \texttt{4f}: Iceberg cannot store
a truncated maximum that is \emph{below} some real value, so it increments the
last kept character to produce a bound that is still an upper bound. A
truncated bound is therefore always safe and sometimes loose, and a UUID lookup
gains nothing from it, since the first 16 characters of random UUIDs never
cluster.

The last row of \Cref{tab:ice-lab-lookup} is the \texttt{counts} mode seen from
the read side. With no min/max in the manifest, the planner cannot exclude any of
the 200 sorted files, and plans 200 splits (50 tasks, after grouping). The
Parquet footers of those files still carry row-group statistics, so each task
skips its row groups and the lookup reads only 1.5~MB; but it has opened 200
files to find that out, where the \texttt{truncate} copy opened one.

\conf{write.metadata.metrics.column.<col>} overrides the default per column,
which is the practical lever: set \texttt{full} on the column your biggest
queries filter by most (the specimen's \texttt{order\_ts}, say) and leave wide
free-text columns at \texttt{counts} so their manifests do not balloon for no
pruning benefit.

\section{Bloom filters}
\label{sec:ice-read-bloom}

Min/max statistics prune well for a range predicate, or for a point lookup on
data clustered by that column. They do not prune a point lookup on an unsorted
high-cardinality column --- \Cref{fig:file-stat-ranges}'s top panel. A Parquet
bloom filter, enabled per column with
\conf{write.parquet.bloom-filter-enabled.column.<col>=true}, answers a narrower
question directly --- ``can this row group possibly contain this exact value'' ---
with no false negatives and a tunable false-positive rate.

On the lab it helped, but less than sorting did. The 10-day unsorted copy
decoded 9.7 million rows without a filter and 2.9 million with one, reading 28.9~MB
instead of 60.5~MB: about two thirds of the row groups were skipped. All 10 files
were still opened, because the filter lives inside the file, below the manifest
layer. And not every row group was skipped, since a bloom filter has false
positives and the column holds about a million distinct values per row group,
more than the default size cap
(\conf{write.parquet.bloom-filter-max-bytes}, 1~MB, per row group) can
represent at a tight false-positive rate. It costs write-time CPU and file size
(the bloom copy is 35.8~MB per file against 34.8~MB), and is worth enabling only
on columns queried by equality that you cannot sort by.

\section{Vectorized reads}
\label{sec:ice-read-vectorized}

\conf{read.parquet.vectorization.enabled} (default \texttt{true}) reads a
\emph{batch} of rows into a columnar, Tungsten-friendly in-memory format
(\Cref{ch:tungsten}) per call instead of materializing one Java object per row.
\conf{read.parquet.vectorization.batch-size} (default 5,000) sets how many rows
make up one batch; larger batches amortize per-batch overhead further but hold
more decoded data in memory at once.

You can see whether it is on from the plan: with it enabled, the scan is followed
by a \texttt{ColumnarToRow} node, which converts the batches the scan produces;
with it disabled, the node is absent. The lab ran one aggregate over 9.7 million
rows both ways:

\begin{table}[htbp]
\centering\footnotesize
\renewcommand{\arraystretch}{1.25}
\begin{tabular}{@{}lrrr@{}}
\toprule
\textbf{Setting} & \textbf{\texttt{ColumnarToRow} in plan} & \textbf{Median task} & \textbf{Bytes read} \\
\midrule
vectorization on & yes & 101~ms & 19.5~MB \\
vectorization off & no & 721~ms & 19.5~MB \\
\bottomrule
\end{tabular}
\caption{The same scan with vectorized reads on and off. The bytes read are
identical; decoding row by row made each task about seven times slower.}
\label{tab:ice-lab-vectorization}
\end{table}

The I/O is the same and only the decoding differs, which is why the setting
belongs to the read path and not to pruning. Leave it on; turn it off only to
isolate a suspected reader bug.

\section{Split planning}
\label{sec:ice-read-splits}

\Cref{sec:shape-jobs} described input partitions as roughly
\conf{read.split.target-size} (128~MB default) worth of data each. For an
Iceberg scan that is the configured \emph{ceiling}, and not always the number you
get. The planner bins manifest entries toward the target, using
\conf{read.split.open-file-cost} (4~MB default) as a floor weight per file so
that many tiny files are not treated as free to combine, and
\conf{read.split.planning-lookback} (10) to bound how many candidate bins it
considers at once.

On the lab the ceiling did nothing, and the cause is a feature. The 10 unsorted
files total 348~MB. At the 128~MB default the arithmetic says about 4 splits,
and the scan ran 10 tasks; setting \conf{read.split.target-size} to 512~MB
changed nothing. Iceberg 1.6 shrinks the target when the scan is small relative
to the cluster's default parallelism (\conf{read.split.adaptive-size.enabled},
default \texttt{true}), so that a small scan still produces enough tasks to keep
the slots busy; here the lab's 40-slot parallelism pulled the target well below
a file. \Cref{tab:ice-lab-splits} turns the adaptive size off to expose the
setting underneath.

\toprule

\midrule

The 128~MB row is the packing the earlier arithmetic predicted: 35~MB files, three
per bin, ten files in four bins. The last row is the other limit: a split can
only fall on a row-group boundary, and these files report no split offsets, so a
smaller target does not create more tasks. For a scan to feed a large cluster,
the data must be in more files than slots, or in files whose row groups can be
split.

\section{The metadata tables as a diagnostic}
\label{sec:ice-read-metadata-tables}

Every layer above is inspectable directly, without guessing from query latency.
\Cref{lst:ice-read-meta} runs the three most useful metadata tables against the
lab's \texttt{orders}.

\begin{lstlisting}[language=SQL,numbers=none,style=plan,caption={Three metadata tables on \texttt{orders}, with the lab's output},captionpos=b,label=lst:ice-read-meta]
SELECT count(*) AS files, round(avg(file_size_in_bytes)/1e6,1) AS avg_mb,
       sum(record_count) AS rows
FROM lab.db.orders.files;
-- files = 31, avg_mb = 34.8, rows = 30000000

SELECT partition, record_count, file_count
FROM lab.db.orders.partitions ORDER BY partition LIMIT 2;
-- {2026-03-01}  967542  1
-- {2026-03-02}  968774  1

SELECT added_data_files_count, existing_data_files_count
FROM lab.db.orders.manifests;
-- 31, 0     (one manifest holding all 31 files)
\end{lstlisting}

\texttt{table.files} lists every live data and delete file with its size, record
count, and per-column bounds; \conf{table.manifests} shows manifest-level
summaries; \conf{table.partitions} aggregates file counts and sizes per
partition, the fastest way to spot a partition accumulating too many small files
(\Cref{sec:ice-file-size}); \conf{table.snapshots} and \texttt{table.history}
show the commit sequence a scan resolves against. Reading these tables directly
is usually the faster way to confirm a suspicion from the scan counters.

Inside Spark, name a metadata table with its full catalog path
(\conf{lab.db.orders.files}): after \texttt{USE lab.db}, the short form
\texttt{orders.files} is parsed as table \texttt{files} in namespace
\texttt{orders} and fails.

\begin{tip}
The pruning ratio at each layer comes straight from the scan node's counters:
\texttt{skippedDataManifests / totalDataManifest} for the first layer and
\texttt{skippedDataFiles / (skippedDataFiles + resultDataFiles)} for the second.
Compare \conf{resultDataFiles} with the table's file count from
\texttt{table.files} to see how selective the whole scan was.
\end{tip}

\section{Summary}
\label{sec:ice-read-summary}

A scan prunes in layers of increasing cost --- manifest list, manifest entries,
optional bloom filter, row-group statistics --- and reports each layer's work as
counters on the scan node. The first layer works when manifests are clustered by
partition; the second works for any column whose per-file ranges are disjoint,
which is a property of how the table was sorted and written, not of the query.
Metrics modes decide whether the ranges exist at all, and a truncated bound is
always safe and sometimes loose. A bloom filter rescues an unsorted equality
lookup partly, below the file layer. Vectorized reads change decoding speed and
nothing else, and split planning's 128~MB target is a ceiling that Iceberg's
adaptive sizing lowers for a small scan. \Cref{tab:ice-read-levers} turns each
symptom into the evidence and the lever.

\begin{table}[htbp]
\centering\footnotesize
\renewcommand{\arraystretch}{1.25}
\begin{tabular}{@{}P{3.3cm}P{3.9cm}P{3.7cm}P{3.1cm}@{}}
\toprule
\textbf{Symptom} & \textbf{Evidence} & \textbf{Lever} & \textbf{Cost} \\
\midrule
a selective query opens every file & \conf{skippedDataFiles} is 0; \texttt{files} ranges overlap & sort or cluster by the filter column & small files; write cost \\
planning is slow, many manifests & large \conf{totalDataManifest}; few skipped & rewrite manifests so each spans few partitions & a maintenance job \\
min/max is missing for a column & \texttt{lower\_bound} is \texttt{NULL} in \texttt{files} & set the column's metrics mode to \texttt{full} or \texttt{truncate} & larger manifests \\
an equality lookup on an unsorted column & overlapping ranges, high \texttt{rows decoded} & bloom filter on that column & write CPU, file size \\

decoding is the bottleneck & no \texttt{ColumnarToRow} node & \conf{read.parquet.vectorization.enabled=true} & none \\
\bottomrule
\end{tabular}
\caption{The read-path levers: symptom, evidence, lever, and cost.}
\label{tab:ice-read-levers}
\end{table}

The rule the chapter repeats: \textbf{statistics skip files only when the data was
laid out so that they can}. \Cref{ch:iceberg-write} turns from reading the layout
to maintaining it.
