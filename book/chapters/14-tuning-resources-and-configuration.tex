\chapter{Tuning Resources and Configuration}
\label{ch:tuning}

\begin{chapterintro}
Your job runs, but it is slow, or it writes temporary files to disk, or it dies
with an out-of-memory error. This chapter shows how to decide how big each worker
should be and how many pieces to cut the work into. It does not give you a list of
magic numbers. It gives you a way to work the numbers out, and then shows the
measurement that proves each one.

All measurements come from the book's lab: one machine, one Spark process
(\Cref{sec:refenv-lab}). Read them as the \emph{shape} of a curve, such as ``it gets
faster, then flattens'', not as sizes to copy into production.
\end{chapterintro}

\section{Five words you need first}
\label{sec:tuning-words}

Everything in this chapter uses five words. If you know them, skip ahead.

\begin{description}[leftmargin=1.2cm,style=nextline]
\item[Executor] A worker process that runs part of your job. A cluster has many.
\item[Core (or slot)] One executor can run several tasks at the same moment. Each
      \emph{core} is one place where a task can run.
\item[Task] The smallest unit of work. One task processes one partition.
\item[Partition] One slice of your data. Ten partitions means ten tasks.
\item[Spill] When a task needs more memory than it has, it writes temporary data to
      disk and reads it back later. The job still finishes, but it does extra work.
\end{description}

\begin{analogy}
Think of a kitchen. An executor is one kitchen. A core is one cook. The memory is the
counter space, shared by all the cooks. A partition is one order ticket. If four
cooks share a small counter, each has little room, and they keep putting half-made
dishes in the fridge (a spill). Two choices fix that: a bigger counter, or fewer
cooks. Choosing between them is what \Cref{sec:executor-sizing} is about.
\end{analogy}

\section{How big should an executor be?}
\label{sec:executor-sizing}

You choose three numbers for each executor:
\conf{spark.executor.cores} (how many cooks),
\conf{spark.executor.memory} (how big the counter is), and
\conf{spark.executor.memoryOverhead} (extra space outside the counter that Spark
does not manage). The memory chapter (\Cref{ch:execmem}) explained what the counter
is made of. Here we see how it behaves when we change the numbers.

\subsection*{The experiment}

We took one stage and ran it twelve times, each time with a different executor
shape. The stage is a window function over the 30-million-row \texttt{orders}
table. Spark splits the rows by \texttt{customer\_id} into 8 partitions and sorts
each partition by \texttt{order\_ts}, so each partition holds about 3.75 million rows.

The shapes are every combination of three heap sizes (1, 2 and 4~GB) and four core
counts (1, 2, 4 and 8). In the lab, Spark runs as a single process, so that
process is the executor. \Cref{fig:spill-heatmap} shows the result.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{spill-heatmap.pdf}
  \caption{The same stage under twelve executor shapes. Green means no spill, red
  means spill. The red cells form a diagonal: a bigger heap or fewer cores moves
  you out of it. Each cell is one run.}
  \label{fig:spill-heatmap}
\end{figure}

Read the picture first. More memory removes spills. More cores brings them back. So
the thing that matters is not the memory alone, and not the cores alone. It is the
memory \emph{each running task gets}.

\subsection*{Why: the memory each task gets}

Spark does not let a task use the whole heap. It sets aside a shared pool for
sorting, joining and aggregating. The size of that pool is

\[
\text{pool} = (\text{heap} - 300~\text{MiB}) \times 0.6 .
\]

The 0.6 is \conf{spark.memory.fraction}. The lab read the pool size from Spark at
start-up, and the formula matched on all three heaps
(\Cref{tab:tuning-pools}, second column).

All tasks that run at the same moment share this pool. So each task's fair share is

\[
\text{share per task} = \text{pool} \div \text{cores}.
\]

\Cref{tab:tuning-pools} computes it for all twelve shapes.

\caption{The memory pool Spark reported at start-up, and the share each running

\label{tab:tuning-pools}
\end{table}

Now plot the twelve runs against that share (\Cref{fig:spill-vs-share}). They
separate cleanly. Every run with 298~MB per task or less spilled. Every run with
456~MB or more did not.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.9\linewidth]{spill-vs-share.pdf}
  \caption{Disk spill against memory per task. Red dots spilled, green dots did not.
  One threshold, between 298 and 456~MB, splits all twelve runs. It does not depend
  on heap size or on core count separately.}
  \label{fig:spill-vs-share}
\end{figure}

So this stage needs somewhere between 300 and 450~MB for its biggest task. That is
the number a sizing exercise looks for. It is also why ``give it more heap'' is
often the wrong first move: if you also add cores, the share per task does not move.

\begin{note}
\textbf{In one sentence:} a task spills when
\texttt{(heap $-$ 300 MiB) $\times$ 0.6 $\div$ cores} is smaller than what its
biggest piece of work needs.
\end{note}

\subsection*{What did spilling cost?}

Less than you might fear, and less than the cores bought.
\Cref{fig:cores-time-gc} shows the run time falling from 55--57 seconds on one core
to 15.6--16.9 seconds on eight. The three heap sizes lie almost on top of each
other, even though the small heaps spilled 0.4--0.6~GB to disk.

A direct comparison: the 2~GB heap with four cores spilled and took 21.9~s. The
4~GB heap with four cores did not spill and took 20.3~s. That is an 8\% difference
from one run each, which is within normal noise.

Be careful with this result. The lab uses a laptop SSD, and the operating system
caches the spill files in memory, so spilling is cheap here. On a cluster whose
local disks sit across a network, it may not be cheap. This lab cannot tell you.

One cost \emph{does} grow steadily with cores: garbage collection (GC). GC is Java
cleaning up memory it no longer needs, and it pauses your tasks while it works. The
right panel shows total GC time growing from 0.16~s to 1.0--1.8~s as cores go from 1
to 8. More tasks running at once means more live data in the same heap, so the
cleaner has more to do.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{cores-time-gc.pdf}
  \caption{Left: more cores make the stage faster, and the three heap sizes behave
  almost the same. Right: more cores also mean more GC time. Rings mark runs that
  spilled. For this stage, spilling to a fast disk cost less than the noise between
  single runs.}
  \label{fig:cores-time-gc}
\end{figure}

\subsection*{Putting it together: three rules}

\textbf{1. Cores.} More cores make the job faster, until memory per task runs short
or GC grows too much. You are trading three things: speed, the share each task gets,
and GC. A common rule of thumb says ``use at most five cores per executor'' because
of how storage clients behave. The lab has no remote storage, so we did not test it.
Check on your own cluster by comparing the scan time at five and at eight cores on
the same data.

\textbf{2. Memory.} Work backwards from the biggest task's need. For the book's
reference cluster (4 cores per executor, \Cref{app:refenv}), the lab stage needs
300--450~MB per task:
\begin{enumerate}[nosep]
\item Pool needed: $4 \times (300 \text{ to } 450) = 1.2$ to $1.8$~GB.
\item Heap needed: $1.2 \div 0.6 + 0.3 \approx 2.3$~GB, up to $1.8 \div 0.6 + 0.3 = 3.3$~GB.
\item So \conf{spark.executor.memory}\,=\,\texttt{4g} sits above the range, with
      room left for caching (\Cref{ch:caching}). It is a sensible first guess.
\end{enumerate}
This is a prediction for the \emph{reference} data. For your job, replace
``300 to 450'' with your own biggest-task need.

\textbf{3. Overhead.} \conf{spark.executor.memoryOverhead} is the extra memory
outside the heap. Its default is the larger of 10\% of executor memory or 384~MB. It
covers thread stacks, class metadata, off-heap memory if you turned it on, and
PySpark's worker processes. The default is a floor, not a measurement of your job.
If a container is killed and \emph{no Java error appears anywhere}, the overhead was
too small. \Cref{sec:failure-signatures} reproduces that failure on purpose.

\begin{tip}
On Kubernetes the pod's memory limit is executor memory, plus overhead, plus any
off-heap size. If the process goes over, the operating system kills the whole pod
from outside Java, so the Spark log says nothing. Look at the pod's status, not at
the executor's log.
\end{tip}

\section{How many partitions?}
\label{sec:tuning-parallelism}

Executors give you slots. Partitions give you the work to put in them. If there are
fewer partitions than slots, some slots sit idle. If there are far more partitions
than slots, you waste time starting tiny tasks.

For DataFrame and SQL jobs, the setting that matters is
\conf{spark.sql.shuffle.partitions} (see \Cref{sec:shuffle-sizing} and
\Cref{sec:aqe-coalesce}). It sets how many partitions Spark creates after a shuffle.
(\conf{spark.default.parallelism} is the similar setting for the older RDD API; it
defaults to the total core count.)

We tested it from 2 to 5000 partitions on the lab's 8 slots, with AQE off, on two
different stages (\Cref{fig:partitions-vs-slots}). The left stage is limited by
reading input. The right stage is limited by the shuffle.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{partitions-vs-slots.pdf}
  \caption{The same sweep on two stages. Left: when reading dominates, the partition
  count hardly matters until it reaches the thousands. Right: when the shuffle does
  the work, too few partitions leave slots idle and too many add per-task cost. The
  curve drops, flattens, then rises.}
  \label{fig:partitions-vs-slots}
\end{figure}

On the right-hand stage:
\begin{itemize}[nosep]
\item \textbf{2 partitions:} six of the eight slots do nothing. 35.9~s.
\item \textbf{8 partitions} (one task per slot): 10.3~s.
\item \textbf{40 partitions:} 8.8~s, the best result.
\item \textbf{5000 partitions:} 15.7~s, as slow as 4 partitions, but for the opposite
      reason: Spark spends its time starting tasks.
\end{itemize}

On the left-hand stage, the input scan (about 32 tasks) does most of the work, so the
shuffle count barely matters until 1000 and 5000, where scheduling cost shows up.

\textbf{The rule:} use at least as many partitions as slots, and not so many that
each task is tiny. AQE (\Cref{ch:aqe}) can merge small partitions for you, which
protects the upper side. Nothing protects the lower side if the data going into the
shuffle is truly small.

\section{Dynamic allocation}
\label{sec:dynamic-allocation}

A fixed number of executors has two problems. In a long-lived session, executors sit
idle between jobs and waste money. In a burst of work, there is no room to grow.

\conf{spark.dynamicAllocation.enabled} lets Spark rent more executors when work
piles up and give them back when it is quiet:
\begin{itemize}[nosep]
\item It \textbf{adds} executors when tasks have been waiting for more than
      \conf{spark.dynamicAllocation.schedulerBacklogTimeout} (1~s by default).
\item It \textbf{removes} an executor that has been idle longer than
      \conf{spark.dynamicAllocation.executorIdleTimeout} (60~s by default).
\item It stays between \conf{spark.dynamicAllocation.minExecutors} and
      \texttt{.maxExecutors}.
\end{itemize}

\subsection*{The one danger: shuffle files}

After a shuffle, the data sits in files on the executors that wrote it. Later stages
read those files. If Spark gives such an executor back, the files go with it, and the
next stage fails or has to recompute everything.

So Spark will not start dynamic allocation unless you tell it how to protect that
data. In the lab, we turned dynamic allocation on without doing so, and the
application refused to start (\Cref{lst:tuning-da-error}). The message lists the
options: an external shuffle service, shuffle tracking, or decommissioning.

\begin{lstlisting}[language=text,style=plan,caption={Dynamic allocation without a plan for shuffle data (Spark 3.5.2, standalone cluster)},captionpos=b,label=lst:tuning-da-error]
org.apache.spark.SparkException: Dynamic allocation of executors requires
one of the following conditions: 1) enabling external shuffle service through
spark.shuffle.service.enabled. 2) enabling shuffle tracking through
spark.dynamicAllocation.shuffleTracking.enabled. 3) enabling shuffle blocks
decommission through spark.decommission.enabled and
spark.storage.decommission.shuffleBlocks.enabled. 4) (Experimental)
configuring spark.shuffle.sort.io.plugin.class ...
\end{lstlisting}

\subsection*{What shuffle tracking does}

Shuffle tracking (\conf{spark.dynamicAllocation.shuffleTracking.enabled}) is the
simplest option. Spark keeps any executor that still holds shuffle files that a
later job might use.

We tested it on a small standalone cluster: one worker with four cores, executors
of one core each, a maximum of four executors, and a 5-second idle timeout. Each run
did the same three steps: run a job, wait 25~seconds, then run the \emph{same}
DataFrame again, so that the first job's shuffle files could be reused.
\Cref{fig:dynalloc-timeline} shows the number of executors over time.

\begin{lstlisting}[language=text,style=plan,caption={The shape of the dynamic-allocation test},captionpos=b,label=lst:tuning-da-steps]
job 1:  run the query                   -> leaves shuffle files
wait:   25 seconds, no work             -> executors may be released
job 2:  run the SAME DataFrame again    -> reuse files, or recompute?
\end{lstlisting}

\begin{note}
Our first version of this test built a \emph{new} DataFrame for job 2. Spark then
recomputed the first stage no matter what happened to the executors, so the test
measured nothing. Reusing the same DataFrame is what makes the comparison fair.
\end{note}

  \includegraphics[width=\linewidth]{dynalloc-timeline.pdf}

  shuffle files, and tracking keeps all four executors during the wait. Middle: the
  same, but the tracking timeout is 8~s, so the executors are released and job~2
  has to request them again. Right: job~1 leaves no shuffle files, so each executor
  is released after its idle timeout.}

There is a trade here. With tracking, four executors sit idle for 25~seconds
because their files might be needed again. In exchange, job~2 finishes in 0.2~s,
because its first stage is skipped. Without tracking, the executors are released and
job~2 takes 25.6~s to rebuild everything. By default the tracking timeout is
infinite (\conf{spark.dynamicAllocation.shuffleTracking.timeout}), which is the
safest and the most wasteful setting.

An \emph{external shuffle service} avoids the trade: it serves shuffle files
without the executor, so the executor can leave. The lab did not run one, so that
claim rests on the Spark documentation and the mechanism in
\Cref{sec:shuffle-external}, not on a measurement.

\section{The external and push-based shuffle service}
\label{sec:shuffle-external}

Normally a reduce task fetches shuffle files directly from the executor that wrote
them (\Cref{sec:shuffle-write}). That is the dependency dynamic allocation has to
work around. If the executor is removed too early, the fetch fails with a
\conf{FetchFailedException}.

\conf{spark.shuffle.service.enabled} moves file serving into a separate, long-lived
process. The shuffle data stays available after the executor that wrote it is gone,
so scaling down no longer risks losing data. Push-based shuffle
(\Cref{sec:shuffle-push}) builds on the same service to merge blocks before the
reduce side asks for them.

\begin{warning}
This is from the Spark documentation and was \emph{not tested} in the lab. On YARN
the external shuffle service runs inside the NodeManager. On Kubernetes there is no
such service, and dynamic allocation relies on shuffle tracking (above) or on
decommissioning. Before you set \conf{spark.shuffle.service.enabled} on Kubernetes,
confirm from the executor logs that a shuffle service is there. If you set
the key and nothing is listening, you get fetch failures that look exactly like the
problem you were trying to avoid.
\end{warning}

\section{Where a setting comes from}
\label{sec:tuning-precedence}

Have you ever changed a setting and seen no effect? A setting can be given in
several places, and Spark follows a fixed order when they disagree. We set the same
key, \conf{spark.sql.shuffle.partitions}, in every place, one after another, and
asked the running session which value it saw (\Cref{tab:tuning-precedence}).

\begin{table}[htbp]
\centering\footnotesize
\renewcommand{\arraystretch}{1.2}
\begin{tabular}{@{}P{6.2cm}rr@{}}
\toprule
\textbf{Where the key was set} & \textbf{shuffle.partitions} & \textbf{executor.memory} \\
\midrule
properties file only (\conf{spark-defaults.conf} equivalent) & 111 & 3g \\
file and \texttt{--conf} on \texttt{spark-submit} & 222 & 5g \\
file, \texttt{--conf} and \conf{SparkSession.builder.config} & 300 & 5g \\
the above, then \texttt{spark.conf.set} on the running session & 400 & --- \\
\texttt{spark.conf.set("spark.executor.memory", ...)} on the running session & rejected & --- \\
\bottomrule
\end{tabular}
\caption{The value the session reported after each place was added. Each row
overrides the one above it. Settings fixed at start-up, such as executor memory,
cannot be changed once the application is running.}
\label{tab:tuning-precedence}
\end{table}

From strongest to weakest, the order is:
\begin{enumerate}[nosep]
\item \texttt{spark.conf.set} or \texttt{SET} on the running session (SQL settings only),
\item values set in your application code,
\item \texttt{--conf} flags on \texttt{spark-submit},
\item \conf{spark-defaults.conf},
\item Spark's built-in default.
\end{enumerate}

The code layer in our test set only the SQL key, so the memory column carries the
\texttt{--conf} value forward.

The last row of the table is the practical lesson: only SQL settings can change
while the application runs. If a value looks ignored, something stronger in the list
is probably overriding the one you edited. To see which value is really in effect,
ask the session: \conf{spark.conf.get(key)}. That is faster than re-reading files.

\section{What to remember}
\label{sec:tuning-summary}

\begin{itemize}
\item \textbf{Memory per task is what matters.} Pool $= (\text{heap} - 300~\text{MiB})
      \times 0.6$; share $=$ pool $\div$ cores. In the lab, tasks spilled below about
      300--450~MB.
\item \textbf{Cores buy speed and cost GC.} From one to eight cores the stage went
      from 55~s to 16~s. Spilling to a fast local disk cost much less than the cores
      returned.
\item \textbf{Partitions need a floor and a ceiling.} At least the slot count, and not
      so many that task start-up dominates. The best point was a flat range in the
      middle.
\item \textbf{Dynamic allocation needs shuffle protection.} Tracking keeps executors
      alive: 0.2~s for job~2 against 25.6~s when they were released, at the price of
      holding idle executors.
\item \textbf{Settings come from several places.} Only SQL settings can change at
      runtime. When in doubt, ask \conf{spark.conf.get}.
\item \textbf{Not measured here:} the Kubernetes shuffle story. It is a design point
      we could not test on one machine.
\end{itemize}

\begin{exercises}
\item Pick a stage of your own that spills. In the stage page, find the biggest
      task's memory use (\Cref{sec:reading-metrics}). Work out the pool per running
      task, and predict whether halving the cores or doubling the heap removes the
      spill. Then try it.
\item Repeat the partition sweep of \Cref{fig:partitions-vs-slots} on one of your
      stages with AQE off. Where is the bottom of your curve compared to your slot
      count?
\item Run a job, wait longer than \conf{spark.dynamicAllocation.executorIdleTimeout},
      then run a second job that reuses the first job's shuffle. Compare job~2's

      cluster has one) with an external shuffle service.
\end{exercises}
