\chapter{Catalogs and Commits}
\label{ch:catalogs}

\begin{chapterintro}
The catalog is the one component that turns a table name into the location of its
current metadata --- and the point at which a commit becomes atomic. Writing new
metadata is not a commit until the catalog's pointer is swapped to it. When two
writers race, one wins the swap and the other retries. This chapter covers what
a catalog does, how the atomic swap works, and how to
tune retries so a busy table does not fail commits under contention. The
lab raced twelve writers for one table: 34 of 48 commits lost a swap and won on
the second attempt, one gave up after four, and not a single row was lost or
duplicated.
\end{chapterintro}

\section{What a catalog does}
\label{sec:cat-what}

Everything in \Cref{ch:iceberg-spec}'s metadata tree is reachable once you have
the path to the current table metadata file --- the catalog's only job is to
be the durable, atomically-updatable record of that one path per table name.
Concretely, a catalog answers two questions: given \texttt{db.table}, what
metadata file is current, and, on a commit, can I swap that pointer to a new
file \emph{only if} no one else has moved it since I last read it. Nothing
about the manifest tree, delete files, or partitioning from
\Cref{ch:iceberg-spec} lives in the catalog at all --- it is small and simple
by design, because it is the one piece of the whole system every reader and
writer has to agree on synchronously.

Catalogs differ only in \emph{where} that one pointer lives and \emph{how} the
conditional swap is enforced (\Cref{fig:catalog-pointer-types}). The lab uses
the simplest: a file-based catalog whose pointer is a \texttt{version-hint.text}
file naming the latest \texttt{vN.metadata.json}, and whose swap is the creation
of the next numbered file, which fails if that file already exists. That
works on a filesystem with atomic create or rename; Iceberg's documentation
advises against a file-based catalog on object stores whose rename is not atomic,
which is why production deployments use a catalog backed by a service
(\Cref{sec:cat-service}).

\section{Service-backed catalogs}
\label{sec:cat-service}

The lab ran one service-style catalog: Iceberg's JDBC catalog on a SQLite
database. Its pointer is one row of a table \texttt{iceberg\_tables} with columns
\texttt{catalog\_name}, \texttt{table\_namespace}, \texttt{table\_name},
\texttt{metadata\_location} and \texttt{previous\_metadata\_location}; after a
\texttt{CREATE} and one \texttt{INSERT} the row pointed at \texttt{00001-\ldots.metadata.json}
and remembered \texttt{00000-\ldots} as its predecessor. A commit is a conditional
\texttt{UPDATE} that names the old location: replaying a stale writer's update
(old location as the condition) changed \textbf{0 rows}, which is the lost swap.
REST and other service catalogs were not run; the description below is the
mechanism. A service-backed catalog puts
the pointer in a database or a service instead of a file. The commit is then one
request carrying the base metadata file's identity alongside the new one, and the
service rejects it with a conflict if its own record of the current metadata no
longer matches that base --- the same expected-old-value check the file-based
catalog gets from ``create the next file, fail if it exists,'' enforced by the
service's own backing store (a database row, most commonly). Every client, whatever
its language or engine, calls the same small API to read or commit a table, and
the service can offer what a bare file cannot: multi-table transactions, or
credential vending, in which the catalog hands each client short-lived storage
credentials scoped to the one table it asked for. The cost is one more service to
run. Iceberg ships several such implementations; which one a table uses changes
where the pointer lives, not the metadata tree beneath it.

\begin{note}
Every catalog answers the same two questions from \Cref{sec:cat-what}; nothing in
\Cref{ch:iceberg-spec} or the rest of this book depends on which one a table uses.
Pick based on what already exists in the platform and what the ecosystem around the
table needs, not on a claimed metadata-format difference --- there is none.
\end{note}

\section{The atomic pointer swap}
\label{sec:cat-swap}

A commit's actual sequence, regardless of catalog:

\begin{enumerate}
  \item read the current metadata file to get the base snapshot;
  \item build new manifests, a new manifest list, and a new snapshot on top
        of that base, writing all of it to storage --- none of this is
        visible to any reader yet;
  \item write a new table metadata file referencing the new snapshot;
  \item ask the catalog to swap its pointer from the base metadata file to
        the new one, \emph{conditioned on} the pointer still being the base
        file.
\end{enumerate}

Step 4 is the only step that touches shared, contended state; steps 1--3 are
pure writes to storage that never conflict with another writer's steps 1--3,
because each writer is writing its own new files. This is exactly why
Iceberg calls its concurrency model \emph{optimistic}: every writer does the
expensive part assuming it will win, and only the cheap, final compare-and-swap
can fail.

\section{Optimistic concurrency and retries}
\label{sec:cat-retries}

When step 4 fails because another commit already moved the pointer, Iceberg
does not discard the writer's work --- it re-reads the new current metadata
file, re-applies the same logical change on top of it (a new manifest
referencing the same underlying data/delete files, at most a cheap manifest
rewrite rather than a data rewrite), and retries the swap. That rewrite is
cheap specifically because a manifest is a small listing of file paths and
statistics (\Cref{sec:ice-spec-v2}), not the data itself --- its size tracks
the number of files touched by \emph{this} commit, entirely decoupled from
how large the table as a whole has grown. \Cref{tab:cat-retry-props}
controls how persistent that retry is.

\paragraph{Watching it happen.} The lab raced twelve writer threads, each
appending four small batches of 20,000 rows to one table: 48 commits that all
reach step~4 within milliseconds of each other. Most of them lose at least one
swap, and the Iceberg client reports each commit's \emph{attempts} counter.
Two messages show up in the log when a swap loses:

\begin{lstlisting}[language=text,numbers=none,style=plan,caption={Why a commit retried (from the lab's log, trimmed)},captionpos=b,label=lst:cat-conflicts]
CommitFailedException: Version 14 already exists: .../t_race_r4/metadata/v14.metadata.json
CommitFailedException: Cannot commit changes based on stale table metadata
\end{lstlisting}

The first is the file-based catalog's compare-and-swap: two writers both built
\texttt{v14.metadata.json} from the same base, one created it first, and the
second found it already there. The second message is the client noticing
before it tries. Either way the writer re-reads the current metadata and goes
again, without surfacing an error to the job (\Cref{fig:catalog-commit-race}
shows the sequence). \Cref{tab:cat-lab-attempts} and \Cref{fig:commit-attempts}
tally the outcome.

A retry is cheap, as the next section explains, and the lab measured it: a
commit that won on the first try took 0.60~s on average and one that needed a
second attempt 0.92~s, about 0.3~s more. The tail is the cost to watch: the one
commit that needed four attempts took 11.8~s, because each failed attempt backs
off before it goes again. Retries also do not raise the table's ceiling. The 47
successful commits landed over 18~s, about 2.6 per second, and they form one line
in the snapshot log: every snapshot's parent is the previous snapshot, however many
writers there are (\Cref{fig:commit-throughput}).

A table with many concurrent writers hitting the same partitions --- several
streaming jobs upserting into one table, say --- can exhaust the default 4
retries under sustained contention, as one commit of 48 did on the lab; raising \texttt{commit.retry.num-retries}
(a table property, set via \texttt{ALTER TABLE ... SET TBLPROPERTIES}) trades
a slower worst-case commit for a much lower failure rate. It does not help a
table where every writer touches the \emph{same} partition on every commit ---
retries only help when the underlying data actually merges cleanly with the
new base, which \Cref{sec:ice-partitioning}'s partition design controls more
than any retry setting does.

\begin{warning}
Retrying a failed swap is safe because retries re-read the real current state
and reapply on top of it --- it is not blind resubmission of the same
metadata file. A writer that instead cached the base snapshot and kept
resubmitting it would silently lose every commit that happened in between.
\end{warning}

\section{Catalog configuration in Spark}
\label{sec:cat-spark-config}

A catalog is registered per Spark session under a name of your choosing:

\begin{lstlisting}[language=bash,caption={Registering the lab's file-based Iceberg catalog},captionpos=b,label=lst:cat-register]
spark.sql.catalog.lab=org.apache.iceberg.spark.SparkCatalog
spark.sql.catalog.lab.type=hadoop
spark.sql.catalog.lab.warehouse=/lab/warehouse
\end{lstlisting}

Every table reference is then three-part,
\texttt{lab.db.orders}, resolved through that specific catalog ---
which matters the moment more than one catalog is registered (say, a file-based one
for experiments and a service-backed one for shared tables):
the catalog name in the identifier, not any global default, decides which
metadata store and which commit protocol from this chapter actually apply.

\begin{note}
\texttt{org.apache.iceberg.spark.SparkCatalog} has to actually be on the
JVM's classpath for this registration to resolve to anything --- the lab passes the
Iceberg Spark runtime jar with \texttt{--jars}; it is not something set by this
config block alone. A catalog name that fails to resolve with a
\texttt{ClassNotFoundException} rather than a clear catalog-not-found error
is almost always this: the config is correct, the jar is missing from the
engine that tried to honor it.
\end{note}

\section{Summary}
\label{sec:cat-summary}

The catalog's whole job is a name-to-current-metadata-file mapping that can be
swapped atomically; the file-based catalog does this with a create-if-absent of
the next metadata file, a service-backed catalog with a conditional update behind
its API, and neither changes anything about the metadata tree itself.
A commit writes all its new files optimistically, then attempts one
conditional swap; on conflict it re-reads the real current state, reapplies
the same change on top of it, and retries within the bounds of
\texttt{commit.retry.*}, which is the lever to raise for a table under
genuine concurrent-writer contention.

\exercisehead
\begin{exercises}
\item Run twelve writers into the same table concurrently, four commits each.
      Count the commits that needed a second attempt and check that the row count
      equals the rows of the commits that succeeded.
\item Register the same physical warehouse location under two differently
      named catalogs in one Spark session. Confirm both resolve the same
      table to the same current snapshot.
\item Lower \texttt{commit.retry.num-retries} to 1 on a table and reproduce a
      commit failure under two concurrent writers; raise it back and confirm
      both succeed.
\end{exercises}
