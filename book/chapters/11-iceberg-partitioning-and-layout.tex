\chapter{Iceberg Partitioning and Layout}
\label{ch:iceberg-layout}

\begin{chapterintro}
Iceberg partitioning is hidden: you filter on \texttt{order\_ts} and Iceberg
derives the predicate on \texttt{day(order\_ts)} for you, so a query never
references a partition column directly and pruning does not break when the
scheme changes. This chapter covers the partition transforms, evolving a spec
without rewriting history, sort orders and Z-ordering, target file size, and the
write-distribution mode --- the choices that decide how much a reader and a
writer have to move. On the lab, hour partitions turned 31 files into 744 for
no pruning gain, Z-ordering read 3 files for a lookup that a customer sort
needed 43 for, and one viral product made a bucket seven times its neighbours.
Every number is a capture from the lab of \Cref{sec:refenv-lab}.
\end{chapterintro}

\section{Hidden partitioning and partition transforms}
\label{sec:ice-partitioning}

A classic Hive table's partition column is a real column duplicated into the
directory path --- a query has to filter on that exact derived value
(\texttt{WHERE order\_date = '2026-09-20'}) for pruning to fire, and a filter
on the underlying timestamp (\texttt{WHERE order\_ts >= \ldots}) does not
automatically resolve to it. Iceberg's partition spec instead names a
\emph{transform} of a source column --- \texttt{day(order\_ts)},
\texttt{bucket(16, customer\_id)}, \texttt{truncate(4, category)} --- and stores the
computed value in the manifest, not as a queryable column at all. The planner
derives the partition predicate from a filter on the source column itself, so
the specimen query's plain \texttt{order\_ts >= TIMESTAMP '\ldots'} filter
from \Cref{sec:pruning-static} prunes correctly with no partition column ever
appearing in the query text.

\Cref{tab:ice-transforms} covers the transforms this stack uses.

\toprule

\midrule
\texttt{day} / \texttt{hour} & Time-series data filtered by a timestamp range &

  high-volume streams (\Cref{ch:streaming}) \\
\texttt{bucket(n, col)} & High-cardinality key with equality or join

  joins (joins that skip the shuffle when both sides share the same bucket

\texttt{truncate(n, col)} & String or numeric prefix filters & Groups by a

\bottomrule
\end{tabular}

\begin{tip}
Prefer \texttt{day} over \texttt{identity} on a raw timestamp: an
\texttt{identity} partition on \texttt{order\_ts} would create one partition
\emph{per distinct timestamp value}, which is not partitioning at all --- it is
one file per row's worth of metadata. Always partition on a transform coarse
enough to group many rows per partition. The lab tried it on one hour of orders
(40,582 rows): an \texttt{identity} partition on \texttt{order\_ts} wrote 3,600
files of 2.8~KB each, about eleven rows apiece, and took 32.4~s; the same hour
under \texttt{hour(order\_ts)} wrote one 1.4~MB file in 1.8~s.
\end{tip}

\paragraph{Choosing the specimen's actual spec.} The right transform is the
coarsest one that keeps a typical partition's files near the target size, and the
lab measures what finer costs. It wrote the same 30 million rows twice, once
partitioned by \texttt{day(order\_ts)} and once by \texttt{hour(order\_ts)}
(\Cref{fig:partition-granularity}).

A finer transform buys pruning only for queries narrower than the coarser unit.
A one-week query gains nothing from hours and pays for them in file opens, task
overhead, and manifest entries. Too coarse costs on the other side: a
\texttt{month} partition of the first half of March held a single 517~MB file,
and a one-day query against it decoded 11.3 million rows
(\Cref{sec:ice-partition-evolution}). The lab's 35~MB-a-day partitions are
already below the 128~MB floor this chapter's exercises set, which is the signal
to stay at \texttt{day}; \texttt{hour} earns its keep only when a day's volume
passes a few gigabytes and queries routinely ask for a few hours.

\section{Partition evolution}
\label{sec:ice-partition-evolution}

A classic Hive table's partitioning is fixed at creation; changing it means
rewriting every file under the new scheme. Iceberg's partition spec can
change (\texttt{ALTER TABLE \ldots ADD PARTITION FIELD}) without touching a
single existing file, because the transform that produced a file's partition
value is recorded per-manifest, not assumed globally --- old manifests keep
describing old files under the old spec, new manifests describe new files
under the new spec, and a query spans both by evaluating each manifest
against its own recorded spec.

This is why moving from \texttt{month(order\_ts)} to \texttt{day(order\_ts)}
as a table grows is a metadata-only operation, not a maintenance project: new
data lands under the finer scheme immediately, old data keeps the coarser
scheme it was written with, and a query filtering by date prunes correctly
against both --- coarser pruning on the old partitions, finer pruning on the
new ones, with no explicit migration step and no downtime
(\Cref{fig:partition-evolution}).

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{partition-evolution.pdf}
  \caption{After evolving \texttt{orders} from \texttt{month(order\_ts)} to
  \texttt{day(order\_ts)}, both specs coexist under the same current
  snapshot. Old manifests keep describing month-partitioned files; new
  manifests describe day-partitioned files. One scan reads both, pruning
  each manifest against its own recorded spec.}
  \label{fig:partition-evolution}
\end{figure}

The lab built exactly this. A table was partitioned by \texttt{months(order\_ts)}
and loaded with the first 15 days of March, then evolved with \texttt{ALTER TABLE
\ldots{} REPLACE PARTITION FIELD months(order\_ts) WITH days(order\_ts)}, and loaded
with the remaining 16 days. No file was rewritten, and the \texttt{partitions}
metadata table reports both specs side by side:

\begin{lstlisting}[language=text,numbers=none,style=plan,caption={The \texttt{partitions} table of an evolved table (trimmed)},captionpos=b,label=lst:ice-lab-evolved]
spec_id  partition            record_count  file_count
0        {674, NULL}          14,514,604    1      -- month 674 since 1970: Mar 1-15
1        {NULL, 2026-03-16}      968,819    1      -- day partitions from here on
1        {NULL, 2026-03-17}      969,559    1
...                                                 -- 16 day partitions, 34.8 MB each
\end{lstlisting}

A query spans both, but it prunes each at its own granularity.
\Cref{fig:evolution-cost} measures one-day queries against the old and new data.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{evolution-cost.pdf}
  \caption{One day of old data lives in the 517~MB month-partition file and
  decodes 11.3 million rows; one day of new data lives in its own 34.8~MB file
  and decodes 0.97 million. Evolution kept the old data readable, not as fast.}
  \label{fig:evolution-cost}
\end{figure}

Evolution is free of rewrites, and equally free of improvement for history: the
old data keeps its coarse layout until a compaction rewrites it under the new
spec (\Cref{ch:iceberg-write}).

\section{Sort orders and Z-ordering}
\label{sec:ice-sort-order}

A partition spec controls which \emph{files} a filter can skip; a
\emph{sort order} controls how much of the \emph{content} within a kept file
can still be skipped, via the column min/max statistics
\Cref{ch:iceberg-spec}'s manifests already carry per file. Files written
sorted by a column have tight, non-overlapping min/max ranges across files ---
a filter on that column can then skip whole files even within one partition,
the same statistics-based pruning \Cref{sec:c-pushdown} described for row
groups, just at the file level.

A single sort order only helps predicates on the columns it is sorted by,
front to back --- a table sorted by \texttt{(category, customer\_id)} gives
\texttt{category} clean file-skipping and gives \texttt{customer\_id} almost
none, because rows are grouped by category first and only ordered by
customer \emph{within} that grouping.

\emph{Z-ordering} (\texttt{rewrite\_data\_files} with \texttt{sort\_order}
type \texttt{zorder}) fixes exactly that asymmetry by building one sort key
out of \emph{interleaved bits} from several columns, so no single column
gets front-of-key priority. Interleaving means taking each column's bits one
at a time in round-robin order: with two columns $A$ and $B$ whose binary
values are $a_2a_1a_0$ and $b_2b_1b_0$, the Z-order key is
$a_2b_2a_1b_1a_0b_0$. Sorting by that combined key groups rows that are
close in \emph{either} column, because a small change in $A$ or $B$ alone
only flips a few bits near the end of the interleaved key --- rows near
each other in the two-dimensional $(A, B)$ space end up near each other in
the one-dimensional sort order, in both directions at once, at the cost of
neither column getting the clean front-of-key locality \Cref{sec:c-pushdown}
described for a plain sort. This is the right trade when queries filter on
\texttt{category} sometimes and \texttt{customer\_id} other times, rather
than one column consistently.

The lab measured both on 9.7 million rows in about 45 files, with lookups on
\texttt{customer\_id}, on \texttt{product\_id}, and on both
(\Cref{fig:sort-vs-zorder}).

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{sort-vs-zorder.pdf}
  \caption{Data files opened by three lookups on three layouts of the same rows.
  Sorting by \texttt{(customer\_id, product\_id)} makes customer lookups nearly
  free (1 file) and leaves product lookups reading 43 of 43. Z-ordering gives up
  the best case for the other lookup: 24 files for a customer, 3 for a product, 2
  for both.}
  \label{fig:sort-vs-zorder}
\end{figure}

The sorted table behaves exactly as described: the leading column prunes
completely, the second column not at all (43 of 43 files read). Z-order spreads
the pruning: no lookup is as cheap as the sorted layout's best case, but none is
as bad as its worst. Use the one that matches how you query; if one column
dominates, sort by it.

\begin{warning}
\texttt{rewrite\_data\_files} only rewrites files it considers badly sized. The
lab's first sort attempt left most files alone, because they were already near
the 8~MB target, and the customer lookup still skipped just 3 of 44 files.
Adding \texttt{rewrite-all=true} rewrote every file and the same lookup then read
one. Check \texttt{skippedDataFiles} after a sort, not just the procedure's
success message.
\end{warning}

\section{Target file size and the small-files problem}
\label{sec:ice-file-size}

Every file a reader opens costs a fixed overhead --- opening the file, reading
its footer, resolving its schema --- independent of how many rows it holds
(\Cref{sec:shape-jobs}'s input-partition sizing runs into the same fixed cost
from the other direction). A table accumulating many small files, typically
from frequent low-volume commits (a streaming job flushing every micro-batch,
\Cref{ch:streaming}), pays that overhead over and over for little data each
time. \texttt{write.target-file-size-bytes} (512~MB by default) sets what a
write aims for; \Cref{ch:iceberg-write}'s compaction procedures are the
after-the-fact fix for files that already landed too small.

\section{Write distribution modes}
\label{sec:ice-write-distribution}

Before a write's rows are grouped into per-partition files, Spark may need to
shuffle them so that all rows for a given partition value land together
rather than scattered across every task's output --- exactly the shuffle
mechanics from \Cref{ch:shuffle}, applied to a write instead of a read.
\texttt{write.distribution-mode} chooses how:

\begin{description}
  \item[\texttt{none}] writes rows in whatever order the upstream plan already
        produced them, with no shuffle. Cheapest, but every task can touch
        every partition, so a table with many partitions ends up with many
        small files per commit --- one per (task, partition) pair touched.
  \item[\texttt{hash}] (the default for unpartitioned or partitioned tables
        with a defined spec) shuffles by partition value first, so each task
        after the shuffle owns one partition's rows and writes one file for
        it. This is the direct fix for the \texttt{none} mode's small-files
        problem, at the cost of the shuffle itself.
  \item[\texttt{range}] shuffles by a sampled range of the sort order instead
        of a hash, producing files with tighter, non-overlapping value
        ranges --- the write-time complement to \Cref{sec:ice-sort-order}'s
        pruning benefit. A hash sends a given key to the same partition every
        time, but two different keys can land in the same partition or two
        adjacent keys can land in different ones --- a hash has no notion of
        order. Range partitioning needs to know \emph{where} the value
        boundaries between partitions should fall to keep them evenly sized,
        so a lightweight sampling pass reads a small fraction of the rows
        first, estimates the value distribution, and picks boundaries from
        that sample before the real, boundary-aware shuffle runs --- the
        extra planning cost this mode carries.
\end{description}

The modes only differ when the rows reaching the writer are not already grouped by
partition. The lab loaded ten days of \texttt{orders} through a round-robin
repartition into ten tasks, so every task held rows from every day, into a
day-partitioned table under each mode (\Cref{fig:distribution-modes}).

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{distribution-modes.pdf}
  \caption{The same ten days written under each distribution mode. With no
  shuffle, each of the ten tasks wrote one file per day it held, 100 files of
  3.6~MB; with \texttt{hash} or \texttt{range} each day's rows were gathered
  first, giving 10 files of 34.8~MB. The inserts took 25.1, 24.3, and 23.8~s.}
  \label{fig:distribution-modes}
\end{figure}

The shuffle bought a tenfold reduction in files and cost nothing measurable in
this run, because the write itself dominated. \texttt{none} also needs the
fanout writer (\texttt{write.spark.fanout.enabled}), since its input is not
clustered by partition; without it the write fails. If you control the upstream
ordering, as a daily partitioned scan does, \texttt{none} is free; otherwise
\texttt{hash} is the safe default.

For the specimen table, this is the mode that determines what a write does
with the viral product from \Cref{sec:shape-ui}'s skew: under \texttt{hash}
distribution, every row for that one \texttt{product\_id} lands in the same
write task regardless of how many there are, so a write task for that key
can end up far larger than the others --- the write-side version of the
same skew, covered in full in \Cref{sec:ice-write-skew}. The lab shows the
file-size version on \texttt{bucket(16, product\_id)} with \texttt{hash}
distribution (\Cref{fig:bucket-hot-key}): the viral product's bucket held 3.33
million rows in a 110~MB file, while the other fifteen held about 425,000 rows
and 15.4~MB each. The 7.1-times-larger task that wrote it is the straggler of
\Cref{ch:aqe} appearing on the write side.

\section{Summary}
\label{sec:ice-layout-summary}

Iceberg partitioning is hidden behind a transform of a source column, so
pruning works from a plain filter on that column with no partition column in
the query; \texttt{day}/\texttt{hour} suit time-series filters,
\texttt{bucket} suits high-cardinality keys and storage-partitioned joins,
and an \texttt{identity} transform on a high-cardinality column is a
modeling mistake, not a partitioning choice. Evolving the spec is
metadata-only because old files keep the spec they were written under. A
sort order or Z-order tightens the per-file statistics that let a reader
skip whole files inside a kept partition; target file size and the write
distribution mode are what decide whether a write produces a few
well-sized files or many small ones in the first place.
