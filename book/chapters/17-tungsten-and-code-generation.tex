\chapter{Tungsten and Code Generation}
\label{ch:tungsten}

\begin{chapterintro}
Below the plan, a stage does not interpret operators row by row. Tungsten stores
rows as packed off-heap bytes, and whole-stage code generation collapses an
operator subtree into a single generated Java method that the JIT compiles to
tight machine code. This chapter opens that layer: the binary row format,
off-heap memory management, cache-aware computation, and the generated code you
can actually read with \texttt{EXPLAIN CODEGEN}.
\end{chapterintro}

\section{The Tungsten binary row format}
\label{sec:tungsten-row}

A plain JVM object holding a row --- one field per Java object, boxed
primitives, object headers --- is exactly the per-object overhead
\Cref{sec:mem-heap} described, multiplied by every row in every partition.
\texttt{UnsafeRow} avoids it by laying a row out as one contiguous byte
buffer instead of a graph of objects: a fixed-size null-tracking bitset
first, then one 8-byte slot per field (a primitive stored inline, or an
offset-and-length pair pointing into a variable-length region at the end of
the same buffer for a string or binary value). \Cref{fig:unsaferow-layout}
shows this for one row of the specimen's \texttt{orders} table: three fixed
8-byte fields sit inline, while \texttt{product\_id} --- a string, so its
length varies row to row --- carries only an (offset, length) pair in its
fixed slot, pointing further into the same buffer where its actual bytes
live.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{unsaferow-layout.pdf}
  \caption{One \texttt{UnsafeRow}: a null bitset, one 8-byte slot per field,
  and a variable-length region past the last fixed slot. A fixed field's
  slot holds its value directly; a variable field's slot holds an
  (offset, length) pointer into the variable region of the same buffer.}
  \label{fig:unsaferow-layout}
\end{figure}

Reading a field is a direct byte-offset access into this buffer --- for a
fixed field, read 8 bytes at a statically known offset; for a variable
field, read the (offset, length) pair, then read that many bytes starting
at that offset --- with no pointer chasing through a graph of objects and
no per-field object to allocate or garbage-collect. The trade is that every
value must fit this fixed encoding, which is exactly why Catalyst carries a
strict, fully resolved schema (\Cref{ch:catalyst}) all the way to execution
--- the row format has no room for a value whose type or size was not known
in advance.

\section{Off-heap memory management}
\label{sec:tungsten-offheap}

\texttt{UnsafeRow} buffers do not have to live on the JVM heap at all. When
\conf{spark.memory.offHeap.enabled} is set, Tungsten's \texttt{TaskMemoryManager}
allocates fixed-size pages directly from off-heap memory (the same pool
\Cref{sec:mem-model} carved out of the executor's total footprint) using
\texttt{sun.misc.Unsafe}-style raw memory access rather than the JVM's normal
object allocator. A row living in an off-heap page is invisible to the
garbage collector entirely --- not "cheap to collect," but never considered
by a GC cycle at all --- which is the mechanism behind
\Cref{sec:mem-gc}'s claim that off-heap execution memory trades GC pressure
for manual lifecycle management: Spark itself must now free a page
explicitly when a task no longer needs it, work the JVM would otherwise have
done automatically at some GC pause's cost.

Trace one page through its lifecycle to see what "manual" actually means
here. A task building a hash table for the specimen's join over
\texttt{product\_id} asks the \texttt{TaskMemoryManager} for a page --- say
64~KB, Tungsten's usual default page size --- and gets back a raw pointer
into off-heap memory, not a Java object. As matching \texttt{orders} rows
arrive, the task writes each one's \texttt{UnsafeRow} bytes directly into
that page at increasing offsets, tracking how much of the page is used
itself, since nothing else is tracking it. When the page fills, the task
asks for another one; when the task finishes, either successfully or via a
failure that unwinds it, it calls \texttt{freePage()} on every page it
still holds, explicitly returning that memory to the pool. Skip that last
step --- a bug in an operator's cleanup path, not a normal case --- and the
memory is simply gone until the executor JVM itself exits, since no
collector is ever going to notice it is unreachable and reclaim it the way
it would an abandoned Java object.

\section{Cache-aware computation}
\label{sec:tungsten-cache-aware}

A CPU cache miss costs orders of magnitude more than a cache hit, and a
sort or hash operation over an array of object pointers --- the classic JVM
collection layout --- follows a different, effectively random pointer on
every comparison, defeating the cache almost completely. Tungsten's
sort implementation instead packs a compact \emph{(prefix, pointer)} pair per
row into one flat array: the prefix is a fixed-size encoding of enough of
the sort key to resolve most comparisons without ever dereferencing the
pointer, so the hot comparison loop reads sequentially through one small,
cache-resident array, only chasing the pointer to the full row on the rare
comparison the prefix cannot resolve alone. Concretely, sorting the
specimen's \texttt{orders} by \texttt{order\_total} (a \texttt{double}):
the prefix \emph{is} that value's own sortable bit encoding, packed directly
into the fixed-size prefix slot --- so two rows with \texttt{order\_total}
of \$42.50 and \$187.00 are fully ordered by comparing their prefixes alone,
with the pointer to each row's full data never touched at all during that
comparison; the pointer is only followed on the rare case of two rows
sharing the exact same \texttt{order\_total}, where the prefix cannot
distinguish them and a real tie-break against the full row is unavoidable.
For fixed-width numeric keys,
Tungsten goes further with a radix sort, which sorts by key bytes directly
with no comparisons at all.

\section{Whole-stage code generation internals}
\label{sec:tungsten-wholestage}

Interpreting a plan operator by operator means a virtual call and a full
row materialization at every boundary between them --- a filter producing a
row, handed to a project, handed to an aggregate, each step paying function-call
overhead the JIT cannot see through because the call target varies with the
plan. \emph{Whole-stage code generation} collapses a chain of adjacent
operators that support it (marked \texttt{CodegenSupport}, a Scala trait an
operator implements to opt into this fusion, internally) into
one generated Java method, using a \emph{produce/consume} protocol: each
operator's \texttt{produce()} emits the code that generates its rows, and
calls into the next operator's \texttt{consume()} inline rather than through
a virtual dispatch --- the whole fused chain becomes one straight-line loop
the JIT compiler can then optimize as a single unit. The \texttt{*(n)}
markers this produces in a plan were already introduced in
\Cref{sec:wholestage-codegen} and catalogued in \Cref{sec:c-codegen}; what
those two places don't show is what the generated method actually looks
like, which is the point of running \texttt{EXPLAIN CODEGEN} yourself rather
than taking the marker on faith.

\Cref{lst:shape-query}'s stage~1 scan-and-filter of \texttt{orders}
(\Cref{sec:catalyst-explain}'s plan, node \texttt{*(1)}) compiles to
something close to this, trimmed to the produce/consume skeleton:

\begin{lstlisting}[language=text,numbers=none,caption={EXPLAIN CODEGEN, trimmed to the *(1) scan-filter stage},captionpos=b]
== Subtree 1 / 2 (maxMethodCodeSize:389) ==
*(1) Filter (order_ts#12 >= 2026-03-01 AND order_ts#12 < 2026-03-08)
+- *(1) ColumnarToRow
   +- BatchScan orders

Generated code:
final class GeneratedIteratorForCodegenStage1 extends BufferedRowIterator {
  protected void processNext() throws java.io.IOException {
    while (scan_input.hasNext()) {
      InternalRow scan_row = (InternalRow) scan_input.next();
      long scan_value = scan_row.getLong(1);           // order_ts, inline field
      // Filter.consume(): the range check, straight-line, no virtual call
      if (scan_value >= 1772323200000000L
          && scan_value < 1772928000000000L) {
        append(scan_row);                              // -> next operator's consume()
      }
    }
  }
}
\end{lstlisting}

Three unfamiliar names carry the whole mechanism, so before reading the
payoff, here is what each one is. \texttt{BufferedRowIterator} is the base
class every generated whole-stage method extends --- it is Spark's own
plumbing, not something you write, and it is what lets the generated class
plug into the rest of the engine as an ordinary iterator despite being
freshly compiled at runtime. \texttt{InternalRow} is Catalyst's internal
row representation --- the \texttt{UnsafeRow} byte layout from
\Cref{sec:tungsten-row} accessed through this interface, which is why
\texttt{scan\_row.getLong(1)} above is a direct, typed field read rather
than a generic get-and-cast. \texttt{append(scan\_row)} is how one fused
operator hands a row to the next one \emph{inside} the same generated
method: it is not a function return, it is the literal inlined code of the
next operator's \texttt{consume()} step, spliced in at compile time --- the
mechanism the produce/consume protocol described in the abstract a moment
ago, spelled out here in the concrete generated source.

One loop, one method: the scan's \texttt{next()}, the columnar-to-row
conversion, and the filter's comparison all inline into
\texttt{processNext()} with no call back out to a generic \texttt{Filter}
object per row --- this is the whole payoff whole-stage codegen exists for,
made concrete instead of asserted.

\begin{note}
Not everything fuses. An \texttt{Exchange} always breaks the chain --- you
cannot generate one straight-line loop across a network boundary, so codegen
restarts on the far side of every shuffle, exactly the stage boundary
\Cref{sec:catalyst-physical} already described from the other direction. A
sort-merge join itself, despite materializing state per key, does implement
\texttt{CodegenSupport} and fuses like any other operator --- this is why
the specimen's own plan (\Cref{lst:explain-anatomy}) shows \texttt{*(2)
SortMergeJoin Inner (9)} carrying a star rather than breaking the chain.
What genuinely does not fuse is an aggregate whose buffer needs arbitrary
objects (\texttt{ObjectHashAggregate} falling back past its distinct-key
threshold, \Cref{sec:c-agg}) or a row-at-a-time UDF Catalyst cannot
generate code for at all --- both visible as a plan node with no asterisk,
or the codegen number resetting around it.
\end{note}

\section{Expression code generation}
\label{sec:tungsten-expr-codegen}

Beneath whole-stage codegen, an individual Catalyst \texttt{Expression}
(\texttt{a + b * 2}, a \texttt{CASE WHEN}) generates its own Java source
fragment rather than being evaluated through a generic interpreter tree ---
the same "generate code instead of interpreting a tree" idea applied one
level down. A single JVM method has a 64~KB bytecode size limit; a query
with a very wide \texttt{SELECT} or a very deep expression tree can generate
code that would exceed it, and Spark's codegen falls back to splitting the
generated code across multiple smaller methods first; if the schema is wide
enough to cross \conf{spark.sql.codegen.maxFields} (100 columns by default,
the same limit \Cref{sec:wholestage-codegen} named as a whole-stage fusion
boundary), Spark instead gives up on generating code for that expression at
all and falls back to plain, interpreted \texttt{Expression} evaluation ---
a real ceiling worth knowing about, since a query built by tooling that
emits hundreds of generated columns can hit it in practice.

\section{Columnar processing and vectorization}
\label{sec:tungsten-columnar}

\texttt{UnsafeRow} is still fundamentally row-oriented: one contiguous
buffer per row. \texttt{ColumnarBatch} (backed by Arrow-compatible
\texttt{ColumnVector}s) stores a batch of rows the other way, one contiguous
buffer per \emph{column} across many rows --- exactly the layout
\Cref{sec:ice-read-vectorized}'s vectorized Parquet reader produces directly
from the file's own columnar encoding, with no row-oriented conversion step
in between. This is also the representation a Pandas UDF or Arrow-based
Python UDF communicates through, and the reason it is fast is more specific
than "same layout": \texttt{ColumnarBatch} and Arrow's own in-memory format
are close enough in byte-level structure that handing a batch to the Python
process can reuse the same underlying buffers rather than walking the data
and re-encoding it --- the JVM and Python sides read the identical bytes
over shared memory, with no per-value (de)serialization loop in between.
A row-at-a-time Python UDF has no such shortcut: every row crosses the
JVM/Python boundary as its own converted Python object, one round trip per
row instead of one per batch.

\section{Summary}
\label{sec:tungsten-summary}

\texttt{UnsafeRow} replaces one-object-per-row with a packed byte buffer,
optionally living entirely off-heap and thus entirely outside GC's view;
sorting and hashing operate on compact prefix-plus-pointer arrays instead of
following object references, for the sake of the CPU cache. Whole-stage
codegen fuses a chain of operators into one generated method via
produce/consume, visible in \texttt{EXPLAIN}'s \texttt{*(N)} markers and
readable directly via \texttt{EXPLAIN CODEGEN}; expression codegen does the
same one level down, bounded by the JVM's 64~KB method size limit. Columnar
batches are the same cache- and vectorization-friendly idea applied to a
whole batch of rows at once, and are exactly what a vectorized Parquet read
or an Arrow-based UDF already speaks natively.
