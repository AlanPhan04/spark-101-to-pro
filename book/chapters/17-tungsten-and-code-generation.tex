\chapter{Tungsten and Code Generation}
\label{ch:tungsten}

\begin{chapterintro}
Below the plan, a stage does not interpret operators row by row. Tungsten stores
rows as packed off-heap bytes, and whole-stage code generation collapses an
operator subtree into a single generated Java method that the JIT compiles to
tight machine code. This chapter opens that layer: the binary row format,
off-heap memory management, cache-aware computation, and the generated code you
can actually read with \texttt{EXPLAIN CODEGEN}.
\end{chapterintro}

\section{The Tungsten binary row format}
\label{sec:tungsten-row}

A plain JVM object holding a row --- one field per Java object, boxed
primitives, object headers --- is exactly the per-object overhead
\Cref{sec:mem-heap} described, multiplied by every row in every partition.
\texttt{UnsafeRow} avoids it by laying a row out as one contiguous byte
buffer instead of a graph of objects: a fixed-size null-tracking bitset
first, then one 8-byte slot per field (a primitive stored inline, or an
offset-and-length pair pointing into a variable-length region at the end of
the same buffer for a string or binary value). Reading a field is a direct
byte-offset access with no pointer chasing and no per-field object to
allocate or garbage-collect; the trade is that every value must fit this
fixed encoding, which is exactly why Catalyst carries a strict, fully
resolved schema (\Cref{ch:catalyst}) all the way to execution --- the row
format has no room for a value whose type or size was not known in advance.

\section{Off-heap memory management}
\label{sec:tungsten-offheap}

\texttt{UnsafeRow} buffers do not have to live on the JVM heap at all. When
\conf{spark.memory.offHeap.enabled} is set, Tungsten's \texttt{TaskMemoryManager}
allocates fixed-size pages directly from off-heap memory (the same pool
\Cref{sec:mem-model} carved out of the executor's total footprint) using
\texttt{sun.misc.Unsafe}-style raw memory access rather than the JVM's normal
object allocator. A row living in an off-heap page is invisible to the
garbage collector entirely --- not "cheap to collect," but never considered
by a GC cycle at all --- which is the mechanism behind
\Cref{sec:mem-gc}'s claim that off-heap execution memory trades GC pressure
for manual lifecycle management: Spark itself must now free a page
explicitly when a task no longer needs it, work the JVM would otherwise have
done automatically at some GC pause's cost.

\section{Cache-aware computation}
\label{sec:tungsten-cache-aware}

A CPU cache miss costs orders of magnitude more than a cache hit, and a
sort or hash operation over an array of object pointers --- the classic JVM
collection layout --- follows a different, effectively random pointer on
every comparison, defeating the cache almost completely. Tungsten's
sort implementation instead packs a compact \emph{(prefix, pointer)} pair per
row into one flat array: the prefix is a fixed-size encoding of enough of
the sort key to resolve most comparisons without ever dereferencing the
pointer, so the hot comparison loop reads sequentially through one small,
cache-resident array, only chasing the pointer to the full row on the rare
comparison the prefix cannot resolve alone. For fixed-width numeric keys,
Tungsten goes further with a radix sort, which sorts by key bytes directly
with no comparisons at all.

\section{Whole-stage code generation internals}
\label{sec:tungsten-wholestage}

Interpreting a plan operator by operator means a virtual call and a full
row materialization at every boundary between them --- a filter producing a
row, handed to a project, handed to an aggregate, each step paying function-call
overhead the JIT cannot see through because the call target varies with the
plan. \emph{Whole-stage code generation} collapses a chain of adjacent
operators that support it (marked \texttt{CodegenSupport} internally) into
one generated Java method, using a \emph{produce/consume} protocol: each
operator's \texttt{produce()} emits the code that generates its rows, and
calls into the next operator's \texttt{consume()} inline rather than through
a virtual dispatch --- the whole fused chain becomes one straight-line loop
the JIT compiler can then optimize as a single unit. \texttt{EXPLAIN CODEGEN}
prints the actual generated Java source; in the tree-form plan, an asterisk
plus a number (\texttt{*(1)}, \texttt{*(2)}, \ldots) marks which operators
were fused into which generated stage --- operators sharing a number were
compiled together into one method, and a number change marks a boundary
codegen could not cross.

\begin{note}
Not everything fuses. A full sort-merge join or an aggregation with certain
UDFs breaks the chain --- visible as the codegen number resetting, or a plan
node with no asterisk at all --- because their control flow (materializing a
full side of a join, or an opaque function call) does not fit the linear
produce/consume model.
\end{note}

\section{Expression code generation}
\label{sec:tungsten-expr-codegen}

Beneath whole-stage codegen, an individual Catalyst \texttt{Expression}
(\texttt{a + b * 2}, a \texttt{CASE WHEN}) generates its own Java source
fragment rather than being evaluated through a generic interpreter tree ---
the same "generate code instead of interpreting a tree" idea applied one
level down. A single JVM method has a 64~KB bytecode size limit; a query
with a very wide \texttt{SELECT} or a very deep expression tree can generate
code that would exceed it, and Spark's codegen falls back to splitting the
generated code across multiple smaller methods (or, past
\conf{spark.sql.codegen.maxFields}-style limits, disabling codegen for that
expression entirely) to stay under the limit --- a real ceiling worth
knowing about, since a query built by tooling that emits hundreds of
generated columns can hit it in practice.

\section{Columnar processing and vectorization}
\label{sec:tungsten-columnar}

\texttt{UnsafeRow} is still fundamentally row-oriented: one contiguous
buffer per row. \texttt{ColumnarBatch} (backed by Arrow-compatible
\texttt{ColumnVector}s) stores a batch of rows the other way, one contiguous
buffer per \emph{column} across many rows --- exactly the layout
\Cref{sec:ice-read-vectorized}'s vectorized Parquet reader produces directly
from the file's own columnar encoding, with no row-oriented conversion step
in between. This is also the representation a Pandas UDF or Arrow-based
Python UDF communicates through: converting a batch to and from Arrow's wire
format is fast specifically because both sides already agree on a
columnar, contiguous layout, unlike a row-at-a-time Python UDF that must
convert one Python object per row.

\section{Summary}
\label{sec:tungsten-summary}

\texttt{UnsafeRow} replaces one-object-per-row with a packed byte buffer,
optionally living entirely off-heap and thus entirely outside GC's view;
sorting and hashing operate on compact prefix-plus-pointer arrays instead of
following object references, for the sake of the CPU cache. Whole-stage
codegen fuses a chain of operators into one generated method via
produce/consume, visible in \texttt{EXPLAIN}'s \texttt{*(N)} markers and
readable directly via \texttt{EXPLAIN CODEGEN}; expression codegen does the
same one level down, bounded by the JVM's 64~KB method size limit. Columnar
batches are the same cache- and vectorization-friendly idea applied to a
whole batch of rows at once, and are exactly what a vectorized Parquet read
or an Arrow-based UDF already speaks natively.
