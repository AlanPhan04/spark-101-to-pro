\chapter{The Shuffle Framework and the Scheduler}
\label{ch:scheduler}

\begin{chapterintro}
\Cref{ch:shuffle} treated the shuffle as a wall. This chapter builds the wall:
the shuffle manager and its writers, the map output tracker that tells reduce
tasks where to fetch from, the DAG scheduler that cuts a plan into stages, the
task scheduler that places tasks on executors, and the block transfer service
that moves the bytes. It is the machinery behind every stage boundary and every
straggler.
\end{chapterintro}

\section{The shuffle manager and shuffle writers}
\label{sec:sched-shuffle-manager}

Every shuffle on a modern Spark version goes through \texttt{SortShuffleManager}
--- the separate hash-based shuffle manager from early Spark versions was
removed once sort-based shuffle's one-file-plus-index-per-task layout
(\Cref{sec:shuffle-write}) proved strictly better at scale. What varies is
which \emph{writer} a given shuffle uses underneath that one manager, chosen
automatically --- not configured --- from the shuffle's own properties, in
this order:

\begin{table}[htbp]
\centering
\caption{Which shuffle writer a given shuffle gets, in the order Spark checks}
\label{tab:sched-shuffle-writers}
\begin{tabular}{@{}p{4.4cm}p{4.0cm}p{5.4cm}@{}}
\toprule
\textbf{Writer} & \textbf{Fires when} & \textbf{Why it's cheaper} \\
\midrule
\texttt{Bypass\-Merge\-Sort\-Shuffle\-Writer} & no map-side aggregation, and
  partition count $\le$ \conf{spark.shuffle.sort.bypassMergeThreshold}
  (200) & writes one file per partition directly and concatenates them ---
  skips sorting entirely, cheap only because so few files need merging \\
\texttt{Unsafe\-Shuffle\-Writer} & serializer supports relocating serialized
  values without deserializing (Kryo, under most configs), and no
  map-side aggregation & sorts compact \emph{(partition-id, pointer)}
  arrays (\Cref{sec:tungsten-cache-aware}) over already-serialized bytes,
  never reconstructing an object mid-sort \\
\texttt{Sort\-Shuffle\-Writer} & neither precondition above holds (bypass
  threshold exceeded, or the shuffle aggregates) & general fallback: a real
  record-by-record sort by partition (and key, if aggregating) \\
\bottomrule
\end{tabular}
\end{table}

The specimen's stage-2 shuffle read (\Cref{sec:shape-jobs}) is a
\texttt{SortMergeJoin} over 200 partitions --- at exactly the bypass
threshold rather than under it, and sort-merge join needs its input sorted
by key regardless, so both map-side stages (0 and 1) get
\texttt{UnsafeShuffleWriter}: no map-side aggregation, Kryo in play, and
the serialized-sort path is strictly cheaper than a full deserialized sort
for a plain shuffle-then-join. A \texttt{GROUP BY} feeding a
\texttt{HashAggregate} instead would disqualify both the bypass and
serialized writers (aggregation needs the writer to combine values by key
as it sorts) and fall to \texttt{SortShuffleWriter} regardless of partition
count. The upshot: a shuffle you did not particularly optimize is not
necessarily running the expensive general path --- Spark already picks the
cheapest writer whose preconditions hold for that specific shuffle.

\section{The map output tracker}
\label{sec:sched-map-output-tracker}

A reduce task needs to know which executors hold which map task's output
before it can fetch anything --- that registry is the \emph{map output
tracker}. The driver's copy, \texttt{MapOutputTrackerMaster}, is the single
authoritative record, updated every time a map task finishes (with its
output location) and every time an executor is lost (with that executor's
outputs invalidated, which is precisely the trigger behind
\Cref{sec:failure-signatures}'s stage-resubmission behavior). Executors hold
a read-only, periodically-refreshed cache of the same information,
\texttt{MapOutputTrackerWorker}, so that a reduce task can resolve fetch
locations locally most of the time without an RPC to the driver for every
single task.

\section{The DAG scheduler and the task scheduler}
\label{sec:sched-dag-task}

Two schedulers do two different jobs, one layered on top of the other, and
the split matters because they operate on different objects: the DAG
scheduler never sees an individual task's placement, and the task
scheduler never sees the dependency graph. The \textbf{DAG scheduler}
builds the job/stage structure \Cref{ch:shape} and \Cref{sec:shape-deps}
already described (walking RDD lineage backward from an action, cutting a
stage at every wide dependency) and owns the stage-resubmission decision
behind \Cref{sec:failure-signatures}'s fetch-failure recovery --- what is
new here is what it hands off once a stage is ready: a \emph{set of runnable
tasks}, with no further opinion on execution order or placement. The
\textbf{task scheduler} (\texttt{TaskSchedulerImpl}) owns everything past
that handoff: given that set and the current executors, it decides
\emph{which} task runs on \emph{which} executor, honoring the locality
preferences below and retrying a task, up to \conf{spark.task.maxFailures},
on a different executor before giving up on the task entirely. A stage
resubmission from the DAG scheduler and a task retry from the task
scheduler look similar from the UI but are two different components acting
at two different granularities --- one re-running a whole stage's missing
map output, the other re-running one task that failed for a reason
narrower than a lost executor.

\section{RPC and block transfer}
\label{sec:sched-rpc-transfer}

Coordination messages (task assignment, status updates, the map output
tracker's queries) travel over Spark's internal RPC layer, built on Netty;
the actual shuffle bytes travel over a separate path, the
\texttt{NettyBlockTransferService}. The two are kept apart because they
have opposite traffic shapes and opposite failure costs: an RPC message is
small and latency-sensitive --- a slow task-assignment reply stalls
scheduling for every waiting task --- while a shuffle fetch is large and
throughput-sensitive, and can be retried or resumed without threatening the
scheduler's own responsiveness. Running both over one channel would let a
handful of multi-hundred-megabyte block transfers queue up behind (or
starve out) the small control messages the scheduler depends on to keep
moving; separating them means a busy shuffle fetch never blocks the RPC
call that would otherwise reassign a freed task slot. This split is also
what makes the external shuffle service possible at all: it only has to
reimplement the \texttt{NettyBlockTransferService} half as a standalone
process (\Cref{sec:shuffle-external}), with no need to also speak the
scheduler's RPC protocol, because block serving never depended on it.
\Cref{fig:scheduler-components} puts all five pieces from this chapter in
one picture, with the RPC/block-transfer split drawn as the two separate
paths it actually is.

\section{Locality and speculation}
\label{sec:sched-locality-speculation}

Placing a task on the executor that already holds its input data avoids a
network read entirely; the task scheduler ranks candidate executors by
locality level --- \texttt{PROCESS\_LOCAL} (same JVM), \texttt{NODE\_LOCAL}
(same node, different executor), \texttt{RACK\_LOCAL}, then \texttt{ANY} ---
and will wait briefly (\conf{spark.locality.wait}, 3s by default) for a
better-locality slot to free up before falling back to a worse one. The
specimen's stage-0 tasks, reading \texttt{orders} directly from GCS, never
see anything better than \texttt{ANY}: GCS is remote object storage with no
notion of "the node this byte range lives on," so there is no better level
for the scheduler to wait for, and it falls straight through. Locality
still does its job for stage~2's shuffle read, though --- a stage-2 task
scheduled on the same node as one of its map-side executors reads that
executor's block over a local network hop rather than a cross-node one,
still cheaper even though it is not \texttt{PROCESS\_LOCAL}.

Speculation (already introduced as a symptom-level fix in
\Cref{sec:failure-signatures}) is that same task scheduler's mechanism
underneath: once a task has run past \conf{spark.speculation.multiplier}
times the median duration for its stage, it launches a second, speculative
copy on a different executor and accepts whichever attempt's result lands
first. What that earlier discussion left implicit is the layer it operates
at: this is a decision the task scheduler makes about one task, with no
visibility into or coordination from the DAG scheduler's stage-level view
--- consistent with the split above, since a straggler is a single task
problem the task scheduler already owns, not a stage problem that would
need the DAG scheduler involved at all.

\section{Summary}
\label{sec:sched-summary}

One shuffle manager, three writers chosen by preconditions rather than
configuration you set directly: bypass for few partitions, serialized-sort
when the serializer allows it, plain sort otherwise. The map output tracker
is the registry that makes fetching possible and that a lost executor
invalidates, triggering the DAG scheduler's stage resubmission. The DAG
scheduler owns stage-level lineage and boundaries; the task scheduler owns
task placement within a stage, locality, and per-task retry, with
speculation as its answer to a straggler that locality alone cannot explain.
Both RPC coordination and the shuffle bytes themselves travel over the same
underlying Netty-based transport, just on logically separate paths.
