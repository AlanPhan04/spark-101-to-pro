\chapter{Writing and Maintaining Iceberg}
\label{ch:iceberg-write}

\begin{chapterintro}
Copy-on-write rewrites whole files on every update: slow writes, fast reads.
Merge-on-read writes small delete files instead: fast writes, slower reads until
compaction catches up. The choice is a function of your update rate and your read
latency budget, and it commits you to a maintenance schedule --- compaction,
snapshot expiration, orphan-file cleanup --- in a specific order. This chapter
covers the write modes, optimizing \texttt{MERGE}, and running maintenance
without deleting data a reader still needs. On the lab, a one-row update cost
7.9~s and 34.8~MB under copy-on-write and 2.9~s and 4~KB under merge-on-read,
sixty tiny commits became one file and a scan four times faster, and expiring
snapshots reclaimed 35~MB, all measured on the lab of \Cref{sec:refenv-lab}.
\end{chapterintro}

\section{Copy-on-write versus merge-on-read}
\label{sec:ice-write-cow-mor}

Every \texttt{UPDATE}, \texttt{DELETE}, or \texttt{MERGE} against a matched
row is, underneath, one of two things: rewrite the data file that row lives
in with that row changed or removed (\emph{copy-on-write}, CoW), or leave the
data file untouched and record the change as a delete file plus, for an
update, a new data file holding only the changed rows
(\emph{merge-on-read}, MoR, built on \Cref{sec:ice-delete-files}'s delete
files). \conf{write.delete.mode}, \conf{write.update.mode}, and
\conf{write.merge.mode} set this independently per operation type; check a
table's current properties rather than assuming a default, since Iceberg has
changed which mode ships as the default across releases.

The trade is exactly where each mode's name says it is: CoW pays the full
cost of rewriting a file at write time so every subsequent read sees plain
data files with no delete files to merge; MoR pays almost nothing at write
time --- a small delete file, no data rewrite --- and pushes the cost onto
every read until compaction (\Cref{sec:ice-write-compaction}) catches up.
\Cref{tab:ice-cow-mor} is the concrete rule: a table with a low update rate
and latency-sensitive reads wants CoW; a table absorbing frequent small
updates (a streaming upsert, \Cref{ch:streaming}) wants MoR, because CoW
there would mean rewriting the same large file on nearly every micro-batch.

Two details are easy to miss. A merge-on-read \texttt{UPDATE} is recorded as an
\texttt{overwrite} snapshot with one added data file (the new row versions) and
one added delete file (the old ones), not as a \texttt{delete}. And after
\conf{rewrite_data_files} rewrote the affected data file, the \texttt{files}
table still listed the ten delete files: they no longer point at live rows but
were not removed. A follow-up run confirmed it on six deletes: \conf{rewrite_data_files}
with \texttt{rewrite-all} left one delete file standing, \conf{rewrite_position_delete_files}
did not remove it, and the \conf{remove-dangling-deletes} option was rejected by Iceberg
1.6.1 (``Cannot use options [remove-dangling-deletes], they are not supported by the
action or the rewriter BIN-PACK'') --- the option belongs to a later release. That is why read cost
recovered only from 0.35 to 0.31~s.

\section{\texttt{MERGE}, \texttt{UPDATE}, and \texttt{DELETE}}
\label{sec:ice-write-merge}

A row-level operation's \texttt{ON} or \texttt{WHERE} predicate does two
different jobs, and conflating them is the single most common performance
mistake against these tables. If the predicate matches whole partitions ---
resolvable the same way \Cref{sec:pruning-static} resolves a scan filter ---
Iceberg performs a \emph{metadata-only delete}: it drops the file references
from the manifest without reading or rewriting a single row, because no row
inside an untouched partition needed to change. If the predicate only
narrows which \emph{rows} inside a file match, Iceberg has to open those
files, find the matching rows, and rewrite (CoW) or emit deletes for (MoR)
exactly the files that contained a match --- every other file in the table
is untouched either way, provided the predicate lets partition pruning rule
them out first.

\begin{lstlisting}[language=SQL,caption={A predicate on the target's partition column keeps the scan narrow},captionpos=b,label=lst:ice-merge-on]
MERGE INTO orders o
USING staged_orders s
ON o.order_id = s.order_id
   AND o.order_ts >= TIMESTAMP '2026-03-03 00:00:00'
   AND o.order_ts <  TIMESTAMP '2026-03-04 00:00:00'
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;
\end{lstlisting}

Dropping the two \texttt{order\_ts} lines does not change which rows match ---
\texttt{order\_id} alone is still sufficient --- but it removes the one predicate
the planner can resolve against partition values before scanning. The lab merged
the same 1,000 staged rows both ways (\Cref{fig:merge-scan-bytes}): without the
predicate the scan read 200.7~MB across 10 tasks, every day of the table; with it,
35.1~MB in one task. Both rewrote the same single 34.8~MB data file, because the
matching rows lived in one partition either way, so the saving is entirely in the
scan, and the merge ran 16\% faster. A \texttt{MERGE} without a partition
predicate is not wrong; it is a full scan wearing a row-level operation's syntax.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{merge-scan-bytes.pdf}
  \caption{The same \texttt{MERGE}, with and without a static range on the
  partition column in the \texttt{ON} clause. The predicate cut the bytes the
  scan read by 5.7 times.}
  \label{fig:merge-scan-bytes}
\end{figure}

The predicate has to be a filter on the target's own column. A join key alone,
such as equality on the staged table's timestamp, is not a static range and
should not be assumed to prune; check the scan's bytes, as above.

A predicate that matches whole partitions takes the other path entirely. The lab
deleted one day of a ten-day table with a range on \texttt{order\_ts}: the
snapshot was an operation of type \texttt{delete} with one deleted data file and
no added files, the statement took 0.54~s, and no data file was read. That is a
metadata-only delete, the cheapest row-level operation there is.

\section{Write distribution and skew on write}
\label{sec:ice-write-skew}

\Cref{sec:ice-write-distribution} covered \texttt{write.distribution-mode}
for a plain append; a row-level operation inherits the same choice, with one
extra failure mode. A \texttt{MERGE} whose matched rows are concentrated in
a handful of partitions --- a backfill touching one day's data, say ---
shuffles unevenly under \texttt{hash} mode exactly the way a skewed join
does (\Cref{sec:aqe-skew}), except AQE's skew-split machinery is a read-side
mechanism and does not rebalance a write.

The specimen's own viral, heavily-discounted product (\Cref{sec:refenv-orders})
makes this concrete. Say a \texttt{MERGE} runs against a month of \texttt{orders}
to correct a pricing error, matching on \texttt{product\_id}. Under
\texttt{hash} distribution, matched rows shuffle by \texttt{product\_id} before
the rewrite, so every row for the viral product lands in a single shuffle
partition. The lab's join shuffle on the same key showed the shape: one
partition of 72.8~MB against a median of 1.6~MB (\Cref{fig:skew-partition-sizes}),
and the write-side bucket of \Cref{fig:bucket-hot-key} was 7.1 times its
neighbours. The task that draws the viral product's partition does the work of
many while the rest of the stage finishes early and sits idle: the straggler
shape of \Cref{sec:aqe-skew}, except that here it is a rewrite task, and AQE's
join-side skew split does not apply to it. Nothing currently detects or splits an
oversized write task the way AQE does for a read. (Claim --- the write-side
straggler itself was not separately timed on the lab.)

\section{Compacting data files}
\label{sec:ice-write-compaction}

\conf{rewrite_data_files} is the direct fix for both small files
(\Cref{sec:ice-file-size}) and MoR read cost: it rewrites a set of files into
fewer, better-organized ones, in one of three strategies.
\texttt{binpack} (the default) merges small files toward the target size with
no reordering --- cheapest, and sufficient when the only problem is file
count. \texttt{sort} rewrites according to a defined sort order
(\Cref{sec:ice-sort-order}), restoring tight min/max ranges that ordinary
appends erode over time. \texttt{zorder} does the same for several columns
interleaved together, at a higher compute cost, when queries filter on
different columns unpredictably. All three also apply outstanding delete
files to the data they rewrite, which is why running compaction is the
concrete answer to a MoR table whose reads have been getting slower.

The lab measured the small-files case with sixty one-minute appends to a table,
the shape a streaming job leaves behind (\Cref{fig:stream-small-files}). The
table held 60 data files averaging 25~KB; one \texttt{binpack} call rewrote all
60 into a single 1.43~MB file, and a full scan fell from 0.45 to 0.12~s, nearly
four times faster, with identical results.

\section{Rewriting manifests}
\label{sec:ice-write-manifests}

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{stream-small-files.pdf}
  \caption{Sixty tiny commits, then compaction, then a manifest rewrite. Compaction
  fixed the files and the scan time but \emph{added} a manifest; the manifest
  rewrite then merged all 61 into one, with no further change to this small scan.}
  \label{fig:stream-small-files}
\end{figure}

Manifests accumulate their own version of the small-files problem: many
small commits each add a small manifest, and a scan's manifest-list pruning
(\Cref{sec:ice-read-manifest-pruning}) works less well the more, smaller
manifests it has to consult individually. \conf{rewrite_manifests}
consolidates them into fewer, larger manifests with the same entries,
improving planning time without touching a single data or delete file --- a
metadata-only compaction, distinct from and cheaper than
\conf{rewrite_data_files}. On the lab it merged 61 manifests into one, but the
scan time did not move (0.12 against 0.13~s): with sixty small manifests on a
local disk, planning was never the bottleneck. The benefit appears when
thousands of manifests make planning itself slow
(\Cref{sec:ice-read-manifest-pruning}), which this lab does not reach.

\section{Snapshot expiration and orphan files}
\label{sec:ice-write-expiration}

\Cref{sec:ice-snapshots} noted that superseded files stay reachable until
something removes their snapshot from the log --- that something is
\conf{expire_snapshots}: past a retention window, it drops old snapshot
entries and, for any file no longer referenced by \emph{any} remaining
snapshot, deletes the physical file. This is the mechanism that actually
reclaims the disk space compaction's rewrites and a row-level operation's
rewritten files leave behind; skipping it does not corrupt anything, it
just means old files accumulate indefinitely.

\conf{remove_orphan_files} is a different, independent safety net: it
scans the table's storage location directly for files that are not
referenced by \emph{any} manifest at all --- typically the debris of a
failed write that never committed, since a successful commit's files are
always referenced. Because it does its own storage listing rather than
reasoning from snapshots, it needs a generous \texttt{older\_than} window
(the default is three days) to avoid racing an in-flight write that has
written files but not yet committed the metadata referencing them.

The lab ran both on the merge-on-read table left by the update experiment, which
had 12 snapshots and 20 data files in a 386.1~MB directory
(\Cref{fig:expire-orphans}). \conf{expire_snapshots} with only the latest
snapshot retained dropped 11 snapshots, deleted 11 data files, 11 manifests, and
11 manifest lists, and left a 350.8~MB directory: 35.3~MB reclaimed, the one
large data file each superseded snapshot had kept alive. A 5~MB stray file, the
kind a failed write leaves, then added 5~MB that no manifest named.
\conf{remove_orphan_files} first \emph{refused} to run with a one-hour
cutoff (``Cannot remove orphan files with an interval less than 24 hours''); with
the stray file aged three days and a 48-hour cutoff, a dry run listed exactly that
file and the real run removed it, restoring 350.8~MB. The table still counted
9,678,114 rows.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{expire-orphans.pdf}
  \caption{Table directory size through the two cleanup procedures. Expiring
  snapshots frees what superseded history held; a stray file from a failed write
  adds 5~MB until \conf{remove_orphan_files} deletes it.}
  \label{fig:expire-orphans}
\end{figure}

\begin{warning}
Guides disagree on a strict global order for these two procedures, and the
official documentation does not mandate one. The mechanism explains why:
\conf{expire_snapshots} is what makes old files eligible for deletion by
un-referencing them, and it is reasonable to run it before or interleaved
with \conf{remove_orphan_files}, which only ever touches files no
snapshot ever referenced in the first place --- the two operate on disjoint
sets of files by construction, as long as \conf{remove_orphan_files}'s
retention window is wide enough to never touch a write still in flight.
Treat the "run compaction, then expire, then remove orphans" sequencing
some operational guides recommend as a safe default cadence, not a
correctness requirement. \Cref{fig:maintenance-order} shows it, and which step
pays for which.
\end{warning}

\section{Metadata management for streaming tables}
\label{sec:ice-write-streaming}

A streaming job committing every micro-batch (\Cref{ch:streaming}) is the
worst case for every mechanism in this chapter at once, and each consequence
compounds a different cost already covered above. Many small commits mean
many small files, which is \Cref{sec:ice-write-compaction}'s small-files
problem, but arriving continuously rather than from one bad batch job.
They also mean many small manifests, which slows manifest-list pruning
(\Cref{sec:ice-read-manifest-pruning}) on every subsequent read, since more,
smaller manifests must be opened and checked individually to plan the same
scan. And every commit adds one more entry to the table metadata file's
snapshot log (\Cref{sec:ice-snapshots}), so that log --- and the metadata
JSON a client must parse just to resolve the current snapshot, and the
search space time-travel queries walk --- keeps growing for as long as the
stream runs uncompacted, all from normal operation rather than a mistake.
The practical answer
is scheduling all three maintenance operations to run continuously and
automatically against a streaming table --- compaction and manifest
rewriting on a short cadence matched to the commit interval, snapshot
expiration on a looser one --- rather than treating maintenance as an
occasional manual task the way it can be on a table that only receives
periodic batch writes.

\section{Summary}
\label{sec:ice-write-summary}

Copy-on-write and merge-on-read trade write cost against read cost in
opposite directions, set independently per operation type; pick from the
update rate and the read-latency budget, not by default. A row-level
operation's predicate does double duty --- matching rows and, if it also
resolves against partition values, keeping the scan narrow the same way any
other filter does. Compaction and manifest rewriting are metadata- and
data-level cleanups that keep reads fast; snapshot expiration and orphan-file
removal are what actually reclaim disk space, operating on disjoint sets of
files with no single mandated order between them. A streaming table needs
all of this running continuously rather than occasionally.
